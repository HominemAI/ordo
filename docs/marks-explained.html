What [lean] actually means

The three status marks that appear on every rule in the spec documents, what each one obligates us to build, and the one subtlety that has repeatedly decided real work.

The three marks, in one sentence each

[settled] a promise

This rule is decided, final, and the implementation is wrong until it matches. The conformance corpus transcribes settled rules into executing tests; a settled rule with no code is a tracked debt.

We owe: the build, exactly as written.

[lean] a sketch we like

A direction we believe in, written down so it isn’t lost. The details are drafts. Nobody may build against it, cite it as authority, or file its absence as a bug.

We owe: nothing. Not a line.

[open] a question

The document knows a decision is needed and refuses to fake one. Open items collect in the decisions board until someone (you) rules.

We owe: a ruling first, then maybe a build.

Why [lean] exists at all

A spec that may only contain finished decisions goes silent about the future, and then the future gets designed ad-hoc in code. A spec where everything written is binding turns every sketch into an accidental promise. [lean] is the escape from that trap: a place to write “here is the shape we currently like” where it can be read, criticized, and improved while remaining legally nothing. The build gate is real: the parser refuses lean spellings, the checklist files lean items as not owed, and an auditor finding lean-with-no-code finds nothing wrong.

The one-line test If deleting the paragraph tomorrow would break a promise to anyone, it was never [lean].

The subtlety that keeps deciding real work

A mark applies to a sentence, not a section, and one construct can carry different marks on its semantics and its spelling. This split has settled several disputes in this project, so it deserves its own picture:

The cases you’ve already ruled on, re-read through the marks

ConstructSettled part (built)Lean part (not owed)
allocate(total, weights, mode) the arithmetic: exact split, parts sum to total, four modes, both venues agree the call site: each over a list parameter is lean, so the function is built and golden-tested with no legal caller yet
triggers the runtime: event derivation, listener matching, clock, delivery, R-G20’s authorization bound the declaration spelling: -> run x names a routine, and every routine spelling is lean, so when… deliberately does not parse yet
std.E.rollup, under none wholly lean: derivable someday, owed by nobody, absent from the corpus’s NOT_RUN reasons
generated UI §1–§4: descriptors, action discovery, CAS-by-default, headless runtime §5’s block set and layout hints, explicitly illustrative, which is why the Watermelon skin can exist without a spec change

Why this protects you specifically

Every mark is a budget decision you didn’t have to sit in a meeting for. [settled] is where engineering time is already committed; [lean] is R&D parked at zero cost; [open] is the queue of things only you can move. When an audit says “settled-but-unbuilt,” that is a real debt. When something lean is unbuilt, that is the system working. And when a build agent proposes implementing a lean paragraph “while they’re in there”, the refusal is automatic, because shipping a draft freezes it, and the whole point of the mark is that drafts stay cheap to change.
