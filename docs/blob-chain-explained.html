What a blob upload writes into the chain

This is the one ruling left in blob custody. Everything else in the blob plan (docs/plan-blob.md) is built and shipped; this is the question the build surfaced and did not answer (plan-blob.md §8).

the chain / $commandlog the row table the object store missing / gap

1 · What the chain is, in one picture

An ordinary write (a normal field update on a row) runs the write protocol. It reads the row before the change (the before-image) and after the change (the after-image), where an image is just the full set of the row's field values at that moment. It packages both images into a command group (one or more row changes made by one caller action) and appends the group to $commandlog, the append-only table that is the chain. Appending hashes the new group together with the previous hash, so the chain is a running, tamper-evident ledger of every group ever appended.

From that one appended record, three things become possible:

  • Undo / revert can compute the inverse of the group and apply it, because the before-image says what to put back.
  • Triggers fire. converged and written events are derived from command groups, so a listener sees the change.
  • The row's rev (its version counter) moves, so a caller holding an old rev knows it is stale.

2 · What a blob upload does today

PUT /blob/<entity>/<field>/<id> streams the uploaded bytes through the sealing pipeline into the object store, inserts a $blobref row (a reference table row holding the handle, which is a 128-bit opaque id minted for the upload, plus the sealed mime, size, and integrity digest), and then UPDATEs the entity row's column with that handle. All three steps run in one database transaction. It appends no command group.

3 · What is not broken

The garbage-collection floor is still correct. A row's delete does go through the ordinary write protocol, and its before-image is a full-row image, so it carries the blob handle that was in the column at the time of the delete. That before-image sits in the chain, inside the reference set the blob sweep checks before it deletes an object. The gap described in §2 is the record of the upload, not the record that could resurrect a deleted row's file. Deleting a row with a blob field, and reverting that delete, both work correctly today.

What is missing is narrower than "blobs are unaudited": it is specifically that attaching or replacing a file leaves no trace, while a row's deletion (and its later revert) still does.

4 · Why it was not simply fixed: the image

Appending a group is one call: TxConn::append_group (crates/ordo-exec/src/commandlog.rs:183) already takes the same transaction attach holds. The hard part is building the image to append. row_image (crates/ordo-conformance/src/write.rs:2852) is the one function that builds a full-row before/after image today: for a sealed field it also mints a SealedHandle and stores the payload, so the image builder and the payload-minting logic are the same code. It is pub(crate) inside ordo-conformance, so it is not visible to ordo-exec, where the blob door lives.

Writing a second image builder inside ordo-exec would mean two functions independently deciding what "the image of this row" means. If they ever disagree (a field ordering difference, a sealing edge case, a NULL handled differently), the result is not a crash. It is a chain that still verifies (the hash math does not know what a correct image looks like) and a revert that restores the wrong row state.

5 · The three candidates

proposed (a) the door builds the group itself

The blob door builds a converge group in the transaction it already holds, using the shared image builder. Nothing in the current code has to be undone, because attach already writes the column in the right transaction with the guard already checked; it needs to also build images and append.

declined (b) return a handle, assign later

Upload returns a handle; a later ordinary write op assigns it to the column. Refused today: blob is not a legal parameter type (blob_parameter, crates/ordo-sema/src/lib.rs:192): "an op parameter cannot name an object the caller did not put there."

open (c) the door calls the write protocol

Instead of reimplementing a slice of the write protocol, the upload compiles to a converge that the ordinary executor runs, with the handle supplied by the platform rather than by caller-written expression.

6 · The dependent question (§8.2): does the digest ride the image?

The digest already exists. $blobref carries a sealed integrity column (crates/ordo-crypto/src/blobref.rs:111), computed over the plaintext bytes as they stream past and sealed under the space's data-encryption key. BlobPipeline::verify (crates/ordo-blob/src/pipeline.rs:445) opens it and checks a fetched object against it, on every read. The open part is narrower than "should we hash uploads": it is only whether a converge image (the record §8.1 would start writing) carries a copy of that digest.

Timing matters here specifically: adding the digest to the image when §8.1 lands is free, because §8.1 is the commit that first writes a blob image at all. Adding it later is a migration. It moves every chain hash that carries one, because the image is part of what gets hashed.

7 · What is safe to ship without the ruling

Safe, and already shipped

  • the store tier and both bindings (filesystem, S3-compatible)
  • the language change (blob, uri, inline)
  • the sealing pipeline and chunked STREAM
  • caps (body limit, max object size)
  • reference GC and its undo-horizon floor
  • BYO bucket
  • export

Not safe to build until ruled

  • a trigger on file arrival
  • an un-attach surface in undo/redo
  • a history view of file changes
  • log replay that reconstructs blob references

Everything on the left does not depend on the upload being visible in the chain. Everything on the right assumes it is, and none of it exists yet, so building any of it now would build against an assumption §8.1 has not settled.

8 · The decision being asked

Rule between (a) and (c). (b) is declined above, with reasons. Deferring the whole question is legitimate: §7 already fences off what would be built on the wrong assumption, and nothing shipped depends on this ruling landing on any particular schedule.

The builder's recommendation is (a), for three reasons:

  1. it extends what is already shipped: attach keeps its shape and gains an append, rather than being replaced;
  2. the one-builder-two-callers precedent already exists and already works (guard_filter_query, shared by the write protocol, undo, and the blob door);
  3. (c) opens a new executor seam (the write path accepting a platform-supplied value with no caller expression) for exactly one caller, which is a wider change for a narrower benefit.
