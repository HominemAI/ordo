Critique Round Five

The original five expert reviews, re-run across the documentation as it stands. Every finding checked against the code or the running binary, not against a status table.

The last formal re-run was 22 days ago, and every engine in this repository was built after it. So its verdicts were stale, and the right way to answer the question was to run the checks again rather than read the last answer.

The documentation is in materially better shape than the review that produced these findings described. The one new finding is the same pattern that review kept identifying — a developer stopped by what the documents say rather than by the language being hard — and it is the sharpest instance of it so far.

The new finding

W-001

The tutorial teaches a declaration the compiler cannot parse

Major · fixed

Section 13 of the tutorial introduces a routine block as ordinary syntax and spends a page on what is right and wrong about it. The shipping binary cannot read the word at all:

$ ordo check routine.ordo
routine.ordo:1:1: parse error [parse_error]:
    expected a declaration (`domain`, `entity`, `op`), found `routine`

The refusal is the defect, not the absence. The feature being unbuilt was a deliberate decision and a correct one: two of our own documents spell that declaration two different ways, so building either would have picked between them by accident. What the decision missed was a pass over the pages that teach the spelling nobody picked.

The message names three alternatives and stops, so it reads as you made a typo or your copy is out of date. Someone who has followed twelve sections correctly now believes they mistyped something the page told them to write. Searching the tutorial for any warning — not yet, unbuilt, does not compile — returns nothing.

Six documents teach it as working syntax, and the same wall waits behind six other declarations that are reserved and unbuilt. Each will produce the same misleading message the first time somebody writes one.

Fixed, both halves

The refusal now says what state the word is in. Nine reserved-but-unbuilt declarations refuse by name, each saying what it is and where it is specified, rather than listing the three that work:

$ ordo check routine.ordo
routine.ordo:1:1: parse error [parse_error]: `routine` is reserved
    and not implemented: scheduled and reactive rules are specified
    in `definition-language.md` §7 and §8 and no compiler accepts
    one yet — the declaration's spelling is deliberately unsettled
    (checklist 12a, 19c)

And the documents say so. The tutorial carries a notice separating what is settled — the rules about what such a routine may see, which is the point of the section — from the spelling, which is what is actually waiting. Three other documents carry a short form above their first block.

The fix found out why this survived four rounds of review. The first version was written into the wrong branch of the parser. It compiled, it read correctly, and it changed nothing — because the branch it should have been in produces a message that looks identical, character for character. No amount of reading the output could have told the two apart. A unit test caught it.

How the tutorial was tested

Round three closed the old capstone finding by reading the tutorial. This pass compiled it instead. All 24 blocks that look like source were extracted and run through ordo check:

  • 8 compile standing alone.
  • 13 fail only because they are fragments, naming an entity or op an earlier block declares. That is a tutorial building up a program, which is what a tutorial does.
  • 2 are grammar notation, not programs (op name($params) flags = body), and correctly do not compile.
  • 1 fails on purpose — the section titled The compile error that saves you.
  • 1 is W-001.

So the old capstone defect is genuinely repaired, and the method that found this one is now cheap to run again.

The usability findings, one by one

X-074

let was in no onboarding document

Closed

It cost an earlier build its central business rule. It now appears 12 times in the tutorial and 13 times in the syntax examples, which are the two documents the finding named as silent.

X-075

The reserved-word list was incomplete and labeled closed

Closed

There is no hand-written list any more. There is a rule — a word is reserved if it can begin a declaration or a clause — with the words derived under it.

X-076

Routine names in every example broke the identifier rule

Closed

The hyphenated names are gone. The one surviving lease-expiry in the specification is the rule that forbids it, explaining that the hyphen reads as minus.

X-077

Parameter bounds were upper-bound only

Closed

Bounds now carry both a minimum and a maximum, so one constraint no longer has to be written twice and raise two different errors at two different times.

X-078

The app manifest grammar was illustrative

Carried, narrower

The half that failing builds actually tripped on — how a page binds its data — was promoted to normative, and the section now opens by telling the reader its two halves have different status. What stays illustrative is how a metric or a table renders.

X-081

No syntax existed to emit a notification

Docs closed, engine unbuilt

The specification now names the mechanism. The engine has none of it. Two facts rather than one verdict, because a reader of the spec and a reader of the binary would otherwise get different answers.

X-082

The trigger event vocabulary was never enumerated

Closed

It is a closed set now, and an unrecognised kind is a compile error rather than a pattern that silently never fires.

X-083

Far more documentation than code

Inverted

71,108 lines of documentation against 228,646 lines of Rust, roughly one to three. The concern does not describe this repository any more.

The two the last round left open

X-001

Authorization was specified but did not execute

Closed

The headline finding of every round until now. Guards are compiled into the query itself, and five conformance suites exercise them.

X-068

A row limit counted as proof of a bounded query

Half closed

A limit now bounds at the parameter's declared ceiling rather than at whatever number reaches the plan, refused at registration if the parameter has no ceiling and refused at the door if a caller exceeds it. The other half — admitting a limit only where the planner can prove the work stops early — is not done, and is recorded rather than assumed covered.

What this pass did not cover

The last round also carried a dozen findings about correctness, distributed systems and operability. Those are not usability, and usability was the question. They are still carried and still three weeks stale, and a round six over them is worth doing before a first deployment carries data that matters.

Full working, with the evidence for every verdict and the commands behind it, is in docs/critique-consolidated-5.md.
