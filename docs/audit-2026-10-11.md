### The five that matter most

1. **A caller with no token can tell a real op from a made-up one** (finding 26). Send no token and no `X-Ordo-Space`: a real op answers `400 missing_space`, an unknown one `403 access_denied`. The public-door test proves byte-identical denials only with the header present. Pre-existing, and now reachable from every visitor of a public site.
2. **A public read has no bound at all** (finding 27). Quota and rate are skipped for `$anonymous`. Each distinct parameter value is a new cache key, so a visitor can make every call a database read. howto-public.md does not say so.
3. **Anyone can file delegation requests without limit** (finding 28). `POST /auth/delegation/request` takes no token, no human check, and no bound. Each call writes a row kept for a day and a deployment security event, and the named person sees it in `std.delegation.mine`.
4. **The compiler crashes on one character** (finding 29). `op x = …` panics the lexer. `ordo check`, `ordo apply` and the door's apply op all reach it.
5. **Two gaps in the never-block promise** (findings 1 and 2). Delegation calls and `listSpaces` have no deadline, so a hung door hangs them. `more()` still copies every earlier row on each page.

- With no token and no space header, `gate` binds the space before the access check (router.rs:776-781). A known op fails at `bind_space` with `400 missing_space`; an unknown op fails at dispatch (router.rs:502-505) with `403 access_denied`.
- Reproduced with a throwaway test in crates/ordo-api/tests/api.rs (reverted):
  ```
  GET /op/vendorSpend  (no headers)  -> 400 {"error":{"code":"missing_space",...,"op":"vendorSpend"}}
  GET /op/noSuchOp     (no headers)  -> 403 {"error":{"code":"access_denied","message":"missing bearer token"}}
  ```
- crates/ordo-api/tests/api.rs:1139-1141 notes the order and calls it documented.

Fix: when there is no token, answer `door_denial` before binding the space, unless the op is public. The public door already treats a missing space as the deployment's.

**Fixed** in 0be9597c. `gate` answers `door_denial` before binding the space when there is no token, no space and no anonymous door. Test in crates/ordo-api/tests/api.rs: `tokenless_real_and_unknown_ops_answer_alike`. The two bodies match once the echoed op name is masked; the content-length follows that name.

### 27. A public read has no bound, and the guide does not say so

**Severity: Medium.**

- `quota_gate` is skipped for `$anonymous` (crates/ordo-api/src/router.rs:791-793): "its load is bounded by the cache".
- The cache key holds the bound parameters (crates/ordo-api/src/public.rs:191-204). A public op with a parameter gives a new key per value, so a visitor makes every call a miss and a database read. `ORDO_PUBLIC_CACHE_BYTES=0` makes every call one.
- No per-address, per-op or per-tenant limit exists on the public path. No setting bounds it.
- docs/howto-public.md:173-187 "Not built yet" lists rate limits under public writes only. docs/howto-public.md:106-107 says a public read "takes no quota" without saying nothing else bounds it either.
- The board carries it: public-data ask 28 (slow-down by address behind a CDN) is Yours / waiting.

Fix: a line in "Not built yet" ("no limit on public reads yet; put a CDN or a proxy limit in front"), and a per-op miss cap as a setting, since the per-address one waits on proxy mode.

**Fixed** in c7dc5f39 and adfed217. `ORDO_PUBLIC_MISSES_PER_MINUTE` (default 600 per op per node, 0 off) refuses a miss past the cap with `429 quota_exceeded`, naming the setting. Hits are not counted. howto-public.md has "What bounds public reads", recommends a CDN in front, and lists a per-visitor limit under "Not built yet". The per-address limit waits on proxy mode. Tests: `misses_over_the_per_minute_cap_are_refused_until_the_minute_turns` and `a_zero_miss_cap_is_off` (crates/ordo-api/src/public.rs), `public_misses_past_the_cap_are_refused_by_name` (crates/ordo-host/tests/public_path.rs).

### 28. Delegation requests are unauthenticated, unbounded writes

**Severity: Medium.**

- `POST /auth/delegation/request` takes no token (crates/ordo-host/src/auth/delegate.rs:81) and runs no human check. `Ceremony::request` (crates/ordo-host/src/consent.rs:846-946) checks the agent id, the id shapes and the op count, then inserts a `$delegation_request` row and records `requested` in the deployment's security stream (:932-940).
- Rows are deleted only once `expires_at` is a day old (:904-909). Each call keeps a row for `ORDO_DELEGATION_REQUEST_SECS` plus 86,400 s.
- Every row names a real `person`, who sees it in `std.delegation.mine` (:1300).
- One script can grow the request table and the security stream, and fill a person's list, with no secret and no limit. docs/howto-delegation.md:189-191 says only "any caller may ask in a listed agent's name".

Fix: run the human check on the request route when `ORDO_AUTH_HUMAN_CHECK` is on, cap open requests per agent and per person as settings, and say in howto-delegation.md what an unauthenticated route costs until 11-4c lands.

**Fixed** in fb886c28 and adfed217. The request route runs the human check when `ORDO_AUTH_HUMAN_CHECK` is on, before any row is written. `ORDO_DELEGATION_OPEN_PER_AGENT` (1000) and `ORDO_DELEGATION_OPEN_PER_PERSON` (10) cap waiting requests. Over either is `429 delegation_limit`, naming the setting and the value. The SDK's `requestDelegation` takes `human`. howto-delegation.md says what the open route costs. Tests in crates/ordo-host/tests/delegation_consent.rs: `ordo_consent_waiting_requests_are_capped_per_person_and_per_agent`, `ordo_consent_the_human_check_guards_the_request_route`. In clients/ordo-sdk/test/delegation.test.ts: `sends the human token and maps the cap and the human check`.

### 29. The lexer panics on a non-ASCII character after `=`

**Severity: Medium.** A crash on input.

- `op thirsty($today: date filled) = …` makes `ordo check` panic: `crates/ordo-syntax/src/lexer.rs:457:22: end byte index 53 is not a char boundary; it is inside '…'`. The slice `&self.src[self.pos..self.pos + 2]` takes 2 bytes where the next character is 3.
- Reproduced with `target/debug/ordo check` on a 2-line file. docs/definition-language.md:649 and :3190 hold the same `…`.
- Reached by `ordo apply` and the door's apply op: `Fixture::from_source` at crates/ordo-host/src/apply_op.rs:444 and deploy.rs:472 lex the submitted program. The CLI exits on the panic; the door's request task unwinds.

Fix: `self.src.get(self.pos..self.pos + 2)` or `is_char_boundary`, and a `parse_error` naming the character.

**Fixed** in ccb8f36c. The lookahead uses `str::get`, and an unexpected character is named with its code point (`` unexpected character `…` (U+2026) ``). Tests in crates/ordo-syntax/tests/lexer_no_panic.rs: `ellipsis_after_equals_is_a_parse_error_naming_the_character`, `every_character_after_an_operator_lexes_without_panicking`.

### 30. A tenant connection named like a well-known provider is labelled as one

**Severity: Low.**

- `GET /auth/methods` labels a connection by name (crates/ordo-host/src/auth/methods.rs:36-45): `google` becomes "Google". The same `label` is applied to a tenant's own connections (:86-89), so a tenant that names its connection `google` is listed as `{"name":"google","label":"Google","kind":"oidc","tenant":true}`.
- A page that renders `label` shows a "Google" button that goes to the tenant's issuer. howto-sign-in.md says `label` is "the provider's own name for Discord, GitHub, Google and Microsoft", so a page author will trust it.

Fix: label tenant connections by their name as written, or refuse the four reserved names in `std.space.addConnection`.

**Fixed** in 618b37f0. A tenant connection is labelled by its name as written, and howto-sign-in.md says so. Test in crates/ordo-host/src/auth/methods.rs: `a_tenant_connection_is_labelled_as_written`.
