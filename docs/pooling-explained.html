What a connection is, and why three stores can’t share the pool

This walks through the question that turned up a real defect: why does Ordo hold six database connections per deployment, why can three of them not simply move into the request pool to save a connection, and what the flaky ordo-host test suite actually was.

the request pool a single-connection store stuck / refused resolved / fixed

1 · What a connection actually is

A Postgres connection is not a lightweight handle the way an HTTP keep-alive connection is. Each one is a separate operating-system process on the database server, forked to serve that one client for as long as it stays connected. That is the whole reason servers cap how many can exist at once: max_connections defaults to 100, and it is a ceiling shared by every database on that server, not per database and not per application.

This is not incidental to what follows. Every number in this document is a count of live server-side processes, and every one of them is drawn down against the same shared ceiling of 100.

2 · What a pool is, and the detail that matters

Ordo's pool (crates/ordo-exec/src/lib.rs) is a fixed set of connections, sized once at construction. The important detail is when they open: Pool::connect_with dials every one of them, in a loop, before it returns anything to its caller (crates/ordo-exec/src/lib.rs:674-678). A pool configured for size 8 is 8 live server processes the moment the deployment boots, whether or not a single request has arrived yet.

Checking a connection out of the pool is not "is one available". It is taking a permit from a semaphore holding exactly size permits (lib.rs:682, lib.rs:802-840). If every permit is already held, the caller waits up to acquire_timeout (2 seconds by default, lib.rs:140) and then fails with a typed, retryable error, PoolError::Saturated (lib.rs:304, lib.rs:372). The module's own words: "Backpressure surfaces as a fast failure the door can convert to a retryable response, never an unbounded internal queue."

4 · Why the three stores are each size 1

All three (the keystore, the credential store, the principal directory) are built the same way: one background thread, running a current_thread Tokio runtime of its own, holding one connection, reached by a job queue. Every statement any of them issues goes through that one thread, so at most one is ever in flight per store. A pool larger than 1 for a consumer that can only ever use 1 would just be sockets held open and idle. All three modules say this in almost the same words:

keystore.rs:150

“One connection: every statement this store issues is serialized through its single job loop anyway, so a larger pool would only hold sockets open.”

credentials.rs:127-129

“One connection: every statement is serialized through the job loop anyway… It also keeps this store's footprint off the pool the request path shares.”

principal_directory.rs:143-145

“One connection: every statement is serialized through the job loop anyway. Keeps this store's footprint off the pool the request path shares, the same choice PgCredentialStore makes.”

The size-1 argument is airtight on its own: it is about not wasting sockets. But notice the second sentence in two of the three quotes above. That is a different argument, and it is the one that matters more.

5 · Why they must not share the request pool

This is reentrancy, not contention. The two look similar from the outside (both show up as timeouts) but they have different causes and only one of them is a hazard baked into the shape of the code.

A request checks out a connection from the request pool: a TxConn, holding one permit. While it still holds that permit (mid-transaction, before it commits) it calls into the keystore to seal or open a data key. See sealed::put(tx: &TxConn, ...) and sealed::resolve(db: Reader<'_>, keys: &dyn KeyProvider, ...) in crates/ordo-exec/src/sealed.rs:107-159; a live call site holding both at once is resolve_sealed in crates/ordo-exec/src/undo.rs:2107-2120, which is handed a transaction-scoped Reader and a KeyProvider in the same call.

Three things worth naming about this failure mode
  • It is load-triggered. At low concurrency there are always spare permits, so the second checkout succeeds and nothing looks wrong. The left panel above is what testing at low concurrency shows you.
  • It gets worse with a bigger pool, not better. More permits means more requests that can simultaneously reach the point of holding one and wanting a second, which is the precondition for the whole pool locking up at once.
  • From outside it looks like a database problem (timeouts, 503s, "the database is slow") when the database was never the bottleneck. The bottleneck is a topology problem inside one process: a task depending on a second permit from the finite pool it is already occupying a seat in.
The rule, stated plainly A task holding a connection must never need a second one from the same finite pool. That is the entire reason the keystore, the credential store and the principal directory each dial their own connection instead of drawing from the request pool. It is exactly the property PgSessionRevocations gets to skip, because nothing calls it while already holding one of its own permits.

6 · What this cost us: the test suite's connection ceiling

crates/ordo-host/tests/runtime.rs has 16 tests that each spawn a real ordo-host binary to test boot behaviour. This was confirmed by counting every .spawn().expect("spawn") call in the file. Each spawned binary is a full deployment: the six connections from §3, sometimes more when a test opens a connection of its own for its own assertions.

The owner's machine has 10 cores, and cargo test's default parallelism runs that many tests at once inside one binary. Sixteen tests that each stand up a full deployment, several running concurrently, adds up fast. It was measured directly rather than estimated: the roadmap entry for this (17ad, 2026-09-24) records that runtime.rs peaks at 99 client backends on its own against Postgres's default max_connections = 100. Put the cluster's limit back to 100 after it had been raised for testing, and runtime.rs fails four tests every time, all four with the same error: FATAL: sorry, too many clients already.

That is why the suite failed a different subset of its tests on almost every run for weeks, and why running it with --test-threads=1 always passed: single-threaded, the sixteen deployments never overlap, so the ceiling is never approached.

It was diagnosed as something else for a long time. The flakiness was tracked under checklist item 17ad as a leaked test server: a test that fails between spawning its binary and killing it leaves an orphaned ordo-host process running, and one was found still live 32 hours later. Leaked servers are real, and each one does hold its pool open and make the ceiling worse. They are not what caused it. A workspace re-run with the connection limit raised to 300 came back clean; put back to exactly 100, it fails the same way regardless of whether anything has leaked yet in that run.

Nothing about this was a capacity test. Nobody set out to see how many connections the platform could open under load. The connections were an accident of every one of sixteen tests booting a production-shaped deployment, at once, on a machine with enough cores to run them all concurrently.

7 · What is being changed

The keystore, the credential store and the principal directory are being consolidated onto one shared connection instead of three, taking a deployment from six connections to four, in production as much as in the test suite. This is safe for a reason §5 already established: each store is already fully serialized internally (one job queue, one thread), and none of them is ever called while holding one of the other stores' connections. Merging the three store connections into one is not the same move as merging a store into the request pool; the request pool is the one pool a task can already be holding a permit from when it reaches for another.

The trade Today the three stores are independent: a lock held on the credential table cannot slow down a keystore lookup, because they are different connections entirely. Sharing one connection means they now serialize against each other: a store blocked on a database lock holds up the other two as well as itself. A request does still call into these stores mid-transaction, exactly the shape §5 walked through; what does not change is that it never waits on a second permit from the request pool to do it. What does change is that a slow write on one store (a key rotation, say) now makes a login or a principal lookup wait on the same single connection, where before it would not have. That is a real change in behaviour, not a free one.

8 · What it actually turned out to be

Everything above was written while the diagnosis was still “deployments hold a lot of connections, and the test suite runs a lot of deployments.” That was true and it was not the cause. The cause was one line.

PoolConfig::from_env() did not read ORDO_PG_POOL_SIZE. It read six environment variables and then computed the seventh as min(cores, 8), unconditionally. So the name was a half-truth: ordo_host::runtime read the variable separately when a deployment booted, which meant the server binary honoured it and every test that built a pool directly did not. Those pools dialled eight apiece whatever the environment said.

That is why sizing the spawned servers down worked and setting the same variable for the whole test run did nothing: the two paths were reading different things.

Against Postgres’s stock max_connections = 100, of which about 97 are usable. The cluster needs no change, and neither does CI.

Three things follow, and the third is the one worth keeping.

  • The store consolidation in §7 is still worth having, and it is not what fixed this. It takes a deployment from six connections to four, everywhere, including in production.
  • Raising max_connections to 300, which is what was reached for first, would have worked and would have left the real defect in place with the ceiling moved.
  • The question that found it was “why are we testing that many connections?” Nothing was testing them. A function whose name promised to read the environment quietly ignored the one variable that named its field, and the number nobody could justify was the symptom.
