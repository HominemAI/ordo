What $secevents grows with, and how fast

You asked what exactly is growing, what the implication is, what the growth looks like at one tenant and at a hundred, whether it moves with every change or every rotation, whether it is linear or exponential, and what the workarounds are. This walks the code that answers each question, kind by kind, with the collapse-key fix (plan-opslog.md D1b, already in this tree) as the dividing line between what changed and what did not.

denial path (collapsed) everything else (one entry each) deployment scope (shared, all tenants) bounded / capped

1 · The one rule that decides everything downstream

Recorder::observe (crates/ordo-secevent/src/recorder.rs:348-387) looks at the kind of the thing that just happened and does one of two things. If it is EventKind::Denied, it folds into a windowed accumulator that only becomes a hashed entry when the window closes. For every other kind (KeyReleased, CustodyAction, AuthenticatorLinked, all of it), it builds a StreamEntry::single immediately: one observation, one entry, forever. EventKind::collapses() (event.rs:459-461) is one line: matches!(self, EventKind::Denied(_)). That line is the headline of this whole document. Denials are the kind the design spent its effort bounding. Every other kind pays full price, one row per occurrence, with no cap at all except the outbox and retention described in §6.

2 · Kind by kind, what actually writes an entry

EventKind has thirteen variants (crates/ordo-secevent/src/event.rs:380-449). I grepped every crate in the workspace for a constructor of each one, outside ordo-secevent's own tests. Most of them have no producer at all today.

KindCollapses?Producer, verified
Deniedyes The door, three call sites: ordo-host/src/lib.rs:1192, 1241, 1270 (unverifiable token, non-member, not-live delegation).

CustodyActionno Five sites, all administrative: ordo-exec/src/erase.rs, ordo-exec/src/undo.rs (per-object presence markers on a blob restore), ordo-host/src/attest_ops.rs, ordo-host/src/exit_ops.rs, ordo-host/src/bucket_ops.rs. Operator/platform acts, not request traffic.

This narrows the question more than I expected. Of thirteen defined kinds, only four have a live producer today: denials (collapsed), key releases (not), custody actions (rare, administrative), and the two markers the stream writes about itself. The other seven are either unbuilt or built-and-unwired. So "what is growing" narrows to two things, almost entirely: denials, which are bounded by design, and key releases, which are not, rather than a broad security log accumulating from many directions at once.

3 · What D1b changed, and what it left alone

Before D1b, the deployment stream's collapse key was effectively (scope, subject, op): every deployment-scope observation shares one scope, so the space a stranger probed never entered the key. A sweep across ten thousand spaces at one op degenerated to one open window and one closed entry with count: 10000, indistinguishable in the record from ten thousand retries against a single space (docs/plan-opslog.md §0.3). D1b adds about: Option<SpaceId> to both StreamEntry and CollapseKey (event.rs:610-618, collapse.rs:64-73), carried through by observe (recorder.rs:358-362) whenever routing sends an observation to the deployment scope. Now a hundred-space sweep is a hundred distinct keys.

The per-window cap stays keyed on Scope alone, not on (Scope, about), deliberately (collapse.rs:28-38, :169). If it counted per target, an attacker choosing space ids would be choosing their own budget. DEFAULT_CAP is 256 and the window is 60 seconds (collapse.rs:89,97). So the exact, verified statement is: a sweep now produces at most 256 distinct entries per scope per 60-second window, plus one Suppressed marker for whatever the cap refused, and the whole shape repeats every window for as long as the sweep continues. plan-opslog.md §Q-4 calls this what it is: "a deliberate 256-fold increase in the volume of the artifact under attack, bounded, declared, and cut by retention at the next checkpoint."

4 · The actual growth term: key releases

MeteredKeys::release wraps every KeyProvider::release call. On success it always emits EventKind::KeyReleased at Scope::Deployment, because it calls observe with Relationship::None unconditionally (ordo-host/src/metrics.rs:918), so route() sends it to the deployment scope regardless of who the subject is. The space the release touched rides along as about (:909, D2 in plan-opslog.md), so the entry names which tenant it concerned, but the entry itself lives in the one shared deployment stream, not in that tenant's own space stream. A tenant cannot see their own key-release volume in their own audit view; it is the operator's record, summed across every tenant the deployment serves (event.rs:44-48: "the platform's own custody and key-release events, which belong to the operator and not to any tenant").

And KeyReleased does not collapse. Every successful release is a separate, immediately-hashed entry, with no window and no cap other than the outbox (§6). So the deployment stream's size is, to first order, a running count of every sealed-field read and write the whole deployment has ever served.

What actually calls release, and how many times per write

Reads are cheap: open_sealed (crates/ordo-exec/src/lib.rs:670-683) takes exactly one lease per query, opens every sealed cell the query returned under it, and releases. A read returning 500 rows across three sealed columns is still one KeyReleased entry.

Writes are not. crates/ordo-conformance/src/write.rs calls release once per sealed field to seal the new value (:1472-1475 on create, :3360-3363 on update), and separately, once per sealed field, to mint the image reference the command group carries (seal_image_ref, :3049-3052). crates/ordo-crypto/src/sealed.rs:37-40 states the image cost exactly: "a converge over a sealed field stores the payload twice, once for the before-image, once for the after-image, and a bulk write over N rows stores 2N." So per sealed field touched:

  • create: 1 write-purpose release (seal) + 1 image-purpose release (after-image only, there is no before) = 2 KeyReleased entries.
  • update / converge: 1 write-purpose release + 2 image-purpose releases (before and after) = 3 KeyReleased entries.

In an app developer's terms: a key release is not one per row and not one per request. It is one per sealed field your write touches (roughly tripled on an update, because the chain keeps both sides of the change), and one per query on the read side no matter how many rows or sealed columns that query returns. A form that updates a customer's name (not sealed) and email (sealed) writes one $commandlog group and about three $secevents entries, entirely from the one sealed field.

One wiring gap worth naming, because it changes whether any of this fires at all. MeteredKeys::with_stream is what attaches a Recorder so releases actually reach $secevents; without it, MeteredKeys still increments the Prometheus counter but records nothing durable. Grepping the tree, the only call sites for .with_stream( are ordo-host/src/metrics.rs's own unit tests (:1120, 1159, 1276). The deployment fixture used by ordo-host's integration tests builds MeteredKeys::new(f.keys.clone(), metrics.clone()) with no .with_stream() at all (ordo-host/tests/deployment.rs:190-196). The mechanism is real and correctly built; whether a given deployment's key releases actually land in $secevents depends on one line of bootstrap code that nothing in this tree demonstrates today. Everything below assumes it is wired, because that is the configuration the design and implementation.md call for.

5 · Growth per tenant, and at a hundred

Everything in this table is arithmetic over stated assumptions, not a measurement. Entry size is estimated from the frozen encoding (chain.rs:20-40: 16-byte domain prefix, length-prefixed scope/subject/op/kind, four u64s, a correlation list, an optional trailer). recorder.rs:316-326's own sizing note lands on "~200 bytes an entry", which is what I use below for a KeyReleased entry (short op, one correlation, one about trailer).

ScenarioAssumptionKeyReleased/day~Bytes/day
Quiet tenant 1,000 calls/day, 10% touch sealed data: 60 reads + 40 writes averaging 1 sealed field each 60×1 + 40×2 = 140 ~28 KB
Busy tenant 200,000 calls/day, 20% touch sealed data: 24,000 reads + 16,000 writes averaging 1.5 sealed fields, weighted 2.5 releases/field (mix of create and converge) 24,000×1 + 16,000×1.5×2.5 = 84,000 ~16.8 MB
100 tenants (10 busy + 90 quiet) same per-tenant assumptions, summed, all landing in the one deployment stream (§4) 10×84,000 + 90×140 = 852,600 ~170 MB/day

At the default 90-day retention (Retention::DEFAULT_KEEP_SECS, store.rs:448), that hundred-tenant deployment accumulates on the order of 15 GB in $secevents from key releases alone before the first checkpoint prune reclaims anything, under these assumptions. Compare that to the worst-case denial sweep from §3: 256 entries × ~150 bytes ≈ 38 KB per minute, so even an hour of continuous attack (60 windows) is roughly 2.3 MB, a rounding error next to a single busy tenant's ordinary traffic. The attack path is the one that got engineered attention (bounded, capped, declared); the traffic path is the one actually filling the disk, and nothing bounds it.

6 · Does it grow with every change? With every rotation?

Ordinary writes do not write here. An UPDATE on a non-sealed column runs the write protocol, appends a command group to $commandlog, and never calls KeyProvider::release: nothing in that path touches ordo-secevent at all. Only a write or read that reaches a field marked sealed in the schema takes a lease, and only taking a lease writes an entry. So it grows with every sealed-field read or write, not with every change, and how much of your schema is sealed is a design decision you already control.

Rotation

docs/roadmap-checklist.md item 17i is unchecked, and its own text is blunt: "rotate() has no production caller at all: revocation never opens a new epoch." docs/plan-production-ops.md §1.1 confirms LocalKeyProvider::rotate mints a new epoch and re-seals nothing (custody.rs:686-700). I grepped the tree for epoch_rotated and reseal_completed, the two CustodyAction strings the plan specifies for a rotation, and found neither anywhere outside the plan document itself. I cannot give you a real number for what rotating a space costs $secevents, because the re-seal worker does not exist in this tree. Calling the raw rotate() primitive today mints a key and writes nothing to the security stream at all; it also re-seals nothing, which is a correctness gap far bigger than a logging question.

What the plan specifies, for when 17i lands (plan-production-ops.md §K1): "one key lease per chunk, not per pass": release(space, Purpose::Reseal, correlation) once per chunk of the keyset-paged scan, not once per object or per row, plus two CustodyAction markers, epoch_rotated at the start and reseal_completed at the end. If it ships as designed, a rotation's cost to $secevents is O(chunks), which is a knob (chunk size) the operator sets, not O(objects). That is the designed shape, not a measured one.

7 · Linear or exponential

Linear, not exponential, in every dimension I can find. Per tenant, growth is linear in that tenant's sealed-field read/write volume. Across tenants, it is linear in tenant count, because every tenant's key releases sum into the same uncollapsed deployment stream (§4): double the tenants, double the entries, no multiplicative interaction between them. Under attack, growth is capped at DEFAULT_CAP (256) entries per scope per 60-second window (§3), which is a flat ceiling, not a curve.

What is bounded: the per-window denial cap; the outbox, hard-capped at Recorder::DEFAULT_OUTBOX = 16,384 entries (recorder.rs:326), past which arrivals are refused and declared lost rather than growing unboundedly; and retention, which drops whole prefixes at a verified checkpoint (store.rs module doc, §1) so the stored total never exceeds roughly keep_secs worth of traffic. What is not bounded: the rate itself. Nothing caps how many KeyReleased entries a deployment can produce per second; it is exactly as fast as legitimate sealed-field traffic is fast. Retention controls how much history you keep, not how fast the stream fills between prunes.

8 · Workarounds, with tradeoffs

recommended (a) collapse key releases

Give KeyReleased the same windowed treatment Denied already has: key on (scope, about, purpose), one entry per window with count inside the hashed body. Cuts the dominant term by roughly the window length's worth of traffic (up to 60× under the default window). Costs per-release correlation resolution: today each entry carries the request's own correlation id, which is exactly the handle §4 relies on to join a release back to a command group; a collapsed entry would keep only a bounded sample (CORRELATION_SAMPLE = 4, the same limit denials already accept, event.rs:596).

argue against (b) sample key releases

security-logging-design.md pins, for the sibling stream, "Nothing is sampled. Every observation is recorded, collapsed with its count, or counted into a declared loss; there is no fourth path where an event quietly does not happen." That rule was written for denials, but the reasoning is the same for key releases: a probabilistic audit trail is not an audit trail, and there is already a statistical view of exactly this data, ordo_key_release_total (metrics.rs:124-126), that carries no integrity guarantee and resets on restart. Sampling the security stream would just build a worse, tamper-evident copy of a counter that already exists.

ruled, unbuilt (c) the deployment-log toggle

ORDO_DEPLOYMENT_SECLOG, off turning off deployment-scope recording entirely, is ruled 2026-09-07 and specified in plan-opslog.md §4, but item D3 is unchecked and I found no ORDO_DEPLOYMENT_SECLOG anywhere in the tree. If built, it removes 100% of this growth (all KeyReleased entries are deployment-scope), at the cost of losing every deployment security event, including denial sweeps, while it is off. All-or-nothing, and not available today.

available now (d) tune retention

Retention::deployment_keep_secs already gives the deployment stream its own number, separate from tenant streams (store.rs:422-440, D1b), set via ORDO_DEPLOYMENT_SECLOG_RETENTION_DAYS (store.rs:442). Default is 90 days, same as tenant retention, changeable today with no code change. This bounds the stored total, not the append rate: §5's per-day number is unaffected, only how many days of it you keep on disk.

largest saving, largest loss (e) stop recording successful releases

Removing KeyReleased entirely removes the term that dominates every number in §5. It is also the biggest loss of evidence on the table: implementation.md:488-492 specifies key releases as mandatory deployment-log content precisely because the stream is the only tamper-evident record of which lease touched which space, when. The Prometheus counter is not a substitute: it has no chain, no checkpoint, and resets on every restart.

Recommendation. (d) is a one-line configuration change available today and worth doing regardless of anything else: it costs nothing and directly bounds disk. It does not fix the rate. (a), collapsing key releases the way denials already collapse, is the real fix: the pattern is proven, the `count`-inside-the-hashed-body machinery already exists, and it is the only option here that reduces the dominant term without deleting the evidence it produces. (b) and (e) trade away the property that makes this stream worth having at all, and (c) is not a lever until it ships.

Every claim above cites a file and the line verified against this tree (branch d1-collapse-key) on 2026-09-11. Where a number is estimated rather than read from a measurement (every figure in §5, and the shape in §K1 of §6) the assumption is stated next to it and is not presented as a measured fact.
