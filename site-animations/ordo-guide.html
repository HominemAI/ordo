The Ordo Guide

Ordo is a self-hostable data platform: a stateless service you run in front of your own Postgres, carrying a registered API, built-in identity with passkeys, per-space custody and audit, scheduled automation, and a generated interface. At its center sits a grammar. You declare shapes, queries, writes, and routines once, and the compiler derives everything the platform serves. This guide walks the platform first, then the language beneath it, marking what runs today and what is settled spec.

The platform

A stateless service over your own Postgres: registered API, built-in identity, custody, audit, automation, and interface, all served from one compiled artifact.

A running Ordo deployment is a small stack with one job per layer. Requests enter through ordo-api, which owns the envelope, the access check, idempotency, and page tokens, with no per-op code anywhere. ordo-host wires the compiled program to identity and execution. ordo-exec owns connections, transactions, and the venue gate. Beneath all of it sits Postgres, and the database is yours: Ordo brings no storage engine of its own.

Users and identity, built in

Ordo ships its own credentialing. The AuthProvider registry lives at the deployment level and covers passkeys (WebAuthn), passwords hashed with argon2id, email one-time codes, and OIDC, SAML, and OAuth2 federation. One deployment has one issuer and one method registry, declared in an auth block; a space never defines its own login methods, it uses the deployment's.

A user authenticates once, to the deployment. What they can touch after that is decided per space: membership says whether they are inside a given world at all, and role→op access profiles say which ops they may call there. Sign-in resists enumeration, since begin issues a challenge whether or not the identifier exists.

Passkeys carry extra weight in this design: they are the platform's only source of user presence. Sensitive paths (operator mode, self-serve space creation, linking a new authenticator) demand a fresh WebAuthn user-presence proof, and presence cannot be delegated, so an agent acting on someone's behalf can never mint one. Ordo owns the verification (challenge, RP-id, origin, presence flag, signature, clone counter, all tested) while the browser ceremony belongs to your frontend. The relying-party apex domain is chosen once per deployment; changing it strands every passkey, so it is treated as permanent.

This is the backend-as-a-service surface. Auth, data, API, automation, audit, and interface come from one compiled artifact, on infrastructure you run yourself.

One deployment

A running deployment is a stateless HTTP service fronting a Postgres database you bring yourself. Each node loads independently and holds no persistent state: your database holds the state, and the nodes translate requests into registered operations against it. Postgres is yours to run, scale, and back up.

Run it yourself

To deploy, run ordo apply ./myprogram.ordo --as my-service. The command compiles your program, stores the artifact in Postgres under a content hash, and points the live deployment at it. Every node independently loads the new version, verifies it against the database, and either begins serving or keeps serving the old one.

The load gate performs three checks before any node serves a new version: the artifact's ops compile to valid SQL, every op's inferred shape matches what Postgres reports, and the database schema matches the artifact's DDL exactly. A failure names which ops failed and why, and the node keeps serving the previous version.

Rolling back is ordo rollback --version <hash>, a re-point to a version already stored and verified. The audit chain records every transition, so you can trace when each version was live.

Operating it stays plain. Connections dial at boot, so a wrong host fails at startup instead of on the first customer request. The connection pool (available parallelism, clamped to 2 through 8) is the concurrency bound: nothing executes without a checkout, so request concurrency can never exceed database concurrency. Reads page by keyset, never OFFSET, which skips and repeats rows under concurrent writes; page size is a deployment-wide setting.

A small door for embedding

The public surface is small by design. ordo-api depends on no sibling crate, and five traits define the whole contract: OpRegistry, OpExecutor, AccessChecker, InvalidationBus, and ReplayCache. Implement them and you control how ops execute, who may call them, and how results propagate.

ordo-host is a worked example of fulfilling those traits rather than a framework you must adopt, so Ordo can sit inside a larger system on that seam alone.

The grammar: a whole app in one file

The language at the platform's center: closed, deterministic, one spelling per concept.

Visualize this · The Ordo Flow

Everything the platform serves comes from one compiled artifact, and the artifact comes from a grammar with one spelling per concept: one way to declare a shape, one way to read, one way to write. You author a .ordo file; the compiler derives the schema, the typed API, the permissions surface, the audit log, and the scheduled jobs from it. Nothing about the running app is hand-wired; it all falls out of the source.

The bet behind that rigidity is specific: a grammar strict enough that an LLM either emits it correctly or fails loudly is also the grammar humans can trust. There is no partial credit for a program that almost parses, and no silent fallback when a statement is ambiguous. The compiler stops and names the problem.

Here is a complete, working single-user app: a plant-watering tracker, start to finish.

plantcare.ordo
domain plantcare @ 0.1.0

entity plants {
  name:      text
  room:      text?
  everyDays: duration(ms) = 7d      # watering cadence
}

entity waterings {
  plant -> plants   owned
  at:    date
  by:    text = ""
}

entity alerts {
  key:      text unique             # upsert-by-key lifecycle
  severity: text = "warning"
  title:    text
  status:   text = "active"
}

op thirsty($today: date) =
  plants[name, room, everyDays]  waterings[at]
  sort -waterings.at
  take[plants.id] 1
  | (at <= $today - everyDays) or at is null

op history($plant: id) =
  waterings(plant == $plant)[at, by]
  sort -at
  take 30

op water($plant: id, $by: text, $today: date) =
  set waterings { plant: $plant, at: $today, by: $by }
  set alerts(key == "thirsty:" + $plant) { status: "resolved" }

op addPlant($name: text, $room: text) =
  set plants { name: $name, room: $room }

op pruneLogs($before: date) =
  del waterings(at <= $before)

# routine & route: settled in spec, source spelling being finalized

routine thirstCheck in plantcare {
  trigger every day 09:00Z
  run($today: date):
    each -> set alerts { key: "thirsty:" + plants.id,
                         title: name + " needs water",
                         status: "active" }   # restate so resolved alerts re-raise
}

route alerts.warning -> [push] fallback email
import { domain, entity, op, synth, t, f, src, lit, desc, or, durationLit } from '@hominemai/ordo-cdk';

const plants = entity('plants', {
  name: t.text(),
  room: t.text().optional(),
  everyDays: t.duration('ms').default(durationLit(7, 'd')),
});

const waterings = entity('waterings', {
  plant: t.ref('plants').owned(),
  at: t.date(),
  by: t.text().default(lit('')),
});

const alerts = entity('alerts', {
  key: t.text().unique(),
  severity: t.text().default(lit('warning')),
  title: t.text(),
  status: t.text().default(lit('active')),
});

const thirsty = op('thirsty', { today: t.date() }, (b, p) =>
  b
    .source(src('plants').pick('name', 'room', 'everyDays'), src('waterings').pick('at'))
    .sort(desc(f.waterings.at))
    .take([f.plants.id], 1)
    .where(or(f.at.le(p.today.sub(f.everyDays)), f.at.isNull())));

const history = op('history', { plant: t.id() }, (b, p) =>
  b
    .source(src('waterings').args(f.plant.eq(p.plant)).pick('at', 'by'))
    .sort(desc(f.at))
    .take(30));

const water = op('water', { plant: t.id(), by: t.text(), today: t.date() }, (b, p) =>
  [
    b.set('waterings', { plant: p.plant, at: p.today, by: p.by }),
    b.set('alerts', { status: lit('resolved') }).where(f.key.eq(lit('thirsty:').add(p.plant))),
  ]);

const addPlant = op('addPlant', { name: t.text(), room: t.text() }, (b, p) =>
  [
    b.set('plants', { name: p.name, room: p.room }),
  ]);

const pruneLogs = op('pruneLogs', { before: t.date() }, (b, p) =>
  [
    b.del('waterings', f.at.le(p.before)),
  ]);

// routine & route: not yet offered by the builder — authored in .ordo

export const ordo = synth(
  domain('plantcare', '0.1.0'),
  plants, waterings, alerts,
  thirsty, history, water, addPlant, pruneLogs,
);

That single file is the whole app description. Two commands turn it into a running system. ordo plan shows you the derived diff before anything happens, and ordo apply registers it.

What you get

  • Typed API ops, one per declared op; nothing else is callable
  • A derived Postgres schema, with your identifiers surviving verbatim
  • A generated UI descriptor from shapes and ops, which is headless and renders nothing
  • A runtime permissions surface with role→op profiles, changeable without a redeploy
  • Audit machinery, which is a hash-chained command log under every write
  • Scheduled routines and event routing, once routine/route land
Pre-alpha, spec-first. The parser, DDL lowering, API surface, and command log run today. routine/route source spelling, the always-on worker that fires them, and outbound egress (push/email/SMS) are the named seams still being closed. Nothing here is installable yet.

The language

Shapes, typed ids, pipelines you can watch, and two write verbs with one spelling each.

Visualize this · Writing Ordo

Ordo's grammar covers four things: how you declare a shape, how a row gets its id, how you read, and how you write. Each has exactly one spelling, and each refuses rather than guesses when a statement doesn't fit.

Shapes

A shape is the whole story of a row: type, default, optionality, even custody, all declared once in place.

text? marks a field optional; anything without a ? is required. Defaults are written as literals, so tier: text = "basic" is the entire default, with nothing computed at read time. customer -> customers is a foreign key the grammar guarantees and the database enforces, riding with the space. sealed on memo means that field is ciphertext at rest.

Every entity declares sealed and unique constraints alongside the type, keeping constraint and field always in sync.

market.ordo
entity customers {
  name:  text
  email: text?  sealed indexed unique normalize(lower)
  tier:  text = "basic"
}

entity orders {
  customer -> customers
  placed: date
  status: text = "open"
  total:  money
  memo:   text = ""   sealed
}
import { entity, t, lit } from '@hominemai/ordo-cdk';

const customers = entity('customers', {
  name: t.text(),
  email: t.text().optional().unique().sealed().indexed().normalize('lower'),
  tier: t.text().default(lit('basic')),
});

const orders = entity('orders', {
  customer: t.ref('customers'),
  placed: t.date(),
  status: t.text().default(lit('open')),
  total: t.money(),
  memo: t.text().sealed().default(lit('')),
});

Typed ids

Every row's id is entity-prefixed and time-ordered (like plnt_01J8…), and the server generates it; nothing in Ordo lets an author choose one. The prefix is derived from the entity name so that any id you see anywhere, in a log line or an audit entry, is self-describing without a lookup.

Derivation splits the name at camelCase boundaries, abbreviates each word, and joins with a hyphen (so orderItems becomes orde-item). Two entities may never land on the same prefix; a collision is a compile error naming both offenders:

compiler
[id_key_collision] `orders` and `orderings` both derive id key `orde`
— give one an explicit key: `entity orderings (key: …)`

Reads are pipelines

A read is a pipeline you can watch: filter, shape, sort, cut, evaluated in exactly the order written. There's no free-form SQL underneath it; what you spell is what runs.

market.ordo
op openOrders($cust: id) =
  orders(customer == $cust
         and status == "open")[placed, total]
  sort -placed
  take 3
import { and, desc, f, lit, op, src, t } from '@hominemai/ordo-cdk';

const openOrders = op('openOrders', { cust: t.id() }, (b, p) =>
  b
    .source(src('orders').args(and(f.customer.eq(p.cust), f.status.eq(lit('open')))).pick('placed', 'total'))
    .sort(desc(f.placed))
    .take(3));

Writes: two verbs, derived modes

There is no insert, update, or delete keyword. There are two verbs, set and del, and the write mode is derived from the statement's condition, never spelled separately:

tasks.ordo
op addTask($project: id, $title: text) =
  set tasks { project: $project, title: $title }

op renameTask($task: id, $title: text) =
  set tasks(id == $task) { title: $title }

op purgeDone($project: id) =
  del tasks(project == $project
            and status == "done")
import { and, f, lit, op, t } from '@hominemai/ordo-cdk';

const addTask = op('addTask', { project: t.id(), title: t.text() }, (b, p) =>
  [
    b.set('tasks', { project: p.project, title: p.title }),
  ]);

const renameTask = op('renameTask', { task: t.id(), title: t.text() }, (b, p) =>
  [
    b.set('tasks', { title: p.title }).where(f.id.eq(p.task)),
  ]);

const purgeDone = op('purgeDone', { project: t.id() }, (b, p) =>
  [
    b.del('tasks', and(f.project.eq(p.project), f.status.eq(lit('done')))),
  ]);
ModeWhat triggers itExample
Createno condition, so nothing to address and this makes a rowset tasks { project: $project, title: $title }
Addressedid == …, which specifies exactly one row that is namedset tasks(id == $task) { title: $title }
Bulkany other condition, which is a range matching however many rows that isdel tasks(project == $project and status == "done")
A delete always states its target: bare del tasks does not parse. Delete-everything is spelled del tasks(true), the same statement said on purpose so a reviewer greps for it rather than having a dropped condition quietly become the fallback.

Refusals are the feature

When a statement can't be honored honestly, the compiler stops and names the problem; it never approximates or falls back to something close:

compiler (messages abridged for illustration)
del tasks
  → [parse_error] a delete always states its target — delete-everything
    is del tasks(true), said on purpose

orders(customer == $cust) sort memo
  → [sealed_unsupported] `memo` is sealed — the blind index answers
    equality only, not sort

entity orderings { … }
  → [id_key_collision] `orders` and `orderings` both derive id key
    `orde` — give one an explicit key

Every one of these failures stops the compiler, so you find out before shipping instead of from a support ticket.

From source to Postgres

A two-command contract, exact DDL, and tenancy carried in every primary and foreign key.

Visualize this · Where Rows Live

Ordo derives the database from your source and shows you exactly what will be built, before it builds it. Every entity you declare becomes a real Postgres table.

plan, then apply

ordo plan derives the schema, the API, and the access surface from your source and shows the exact diff (additions, drops, and everything in between) before anything happens. ordo apply takes that plan and stores it as a versioned artifact in the registry.

apply does not run DDL against your database. It registers a versioned, compiled program. What turns that artifact into running schema and endpoints is a separate concern from the language itself; apply's job stops at "this program is now the registered one."

The lowering

Every field lowers to a typed column, with your identifiers surviving verbatim and double-quoted: the same spelling in source, schema, and the command log. A duration(ms) literal like 7d becomes a plain integer of milliseconds, so there's no unit bug waiting in a join.

plantcare.ordo
entity plants {
  name:      text
  room:      text?
  everyDays: duration(ms) = 7d
}
import { entity, t, durationLit } from '@hominemai/ordo-cdk';

const plants = entity('plants', {
  name: t.text(),
  room: t.text().optional(),
  everyDays: t.duration('ms').default(durationLit(7, 'd')),
});
derived DDL
CREATE TABLE "plants" (
  "$space"    text   NOT NULL,
  "id"        text   NOT NULL,
  "name"      text   NOT NULL,
  "room"      text,
  "everyDays" bigint NOT NULL DEFAULT 604800000,
  PRIMARY KEY ("$space","id")
);

Two columns appear on every table whether or not you declared them: "id" and "$space". The primary key is always the pair ("$space","id"), which is what makes tenancy structural rather than a convention someone has to remember to apply.

Tenancy is structural

"$space" rides in every primary key and every foreign key. A row in one space cannot reference a row in another, because the reference itself carries the space it was made in, so there's no query path that lets it happen by accident.

The API

Ops are the only callable surface, which are typed and versioned with nothing else existing to call.

There is no free-form query endpoint. Every callable thing in an Ordo app is an op you declared, and each one compiles to exactly one route.

Ops are the only surface

Each op becomes /op/{name}, singular, never /ops/. Reads use GET; writes use POST. Params are validated at the door, and the response is shaped exactly the way the op's query says.

OpMethod & pathParams
thirstyGET /op/thirsty$today: date
historyGET /op/history$plant: id
waterPOST /op/water$plant: id, $by: text, $today: date
addPlantPOST /op/addPlant$name: text, $room: text
pruneLogsPOST /op/pruneLogs$before: date

Nothing you didn't declare is reachable; there is no ORM escape hatch and no admin query console sitting next to it.

Calling an op

Parameters travel as a bare-keyed JSON body, with no envelope and no wrapper object:

request
POST /op/water
{"plant":"plnt_01J8…","by":"adam"}

Every response carries a per-op version header. If the client's compiled understanding of an op has drifted from what's currently registered, the response comes back flagged rather than silently mismatched. That includes x-ordo-version-skew for callers paging through a result set whose shape changed underneath them.

What you can't see can't hurt you

Authorization lives as runtime platform data: role→op access profiles plus capability allowlists, looked up on every call. Changing who can call what is a data change, live immediately, with no recompile of the domain.

A refused call and a call to an op that was never declared return the same 403 access_denied, byte-identical. There is no signal in the response that distinguishes "you're not allowed" from "that doesn't exist." And the per-caller catalog doesn't mark what you can't reach; it simply omits it, so probing the catalog itself leaks nothing about what exists elsewhere in the app.

Access profiles runs today

Profiles map roles to the ops they can call. For plantcare, a natural progression looks like this:

RoleCan call
viewerthirsty, history
editor+ water
manager+ addPlant
owner+ pruneLogs

These four roles are owner, manager, editor, viewer, the complete set with nothing in the language letting you invent an "admin" or a "member" role. Because profiles are runtime data rather than compiled syntax, you can widen or narrow who calls what without a redeploy. The source that declared pruneLogs never has to change for an owner to be promoted to a manager, or the reverse.

Sovereignty

Custody is set per space, and what can be read is decided by the keys themselves at write time.

Visualize this · Sovereign Spaces

Spaces

Every Ordo deployment divides into spaces. A space is one world of data: its own membership, its own keys, its own command history. Nothing is global by accident: a row, a key, and a chain all belong to exactly one space, and everything else in this section is a property of one space at a time.

A single deployment can host spaces with completely different custody postures side by side. One team's data can sit under platform-managed keys while another's sits fully client-held, in the same database, on the same compiled schema.

The custody dial

Within a space, custody is a dial with three stops. Moving the dial keeps your schema and queries intact; it changes what the database is physically capable of reading.

Dial positionThe database holdsThe platform can read
custody: managedplaintext rows, indexed and sortable normallyeverything (the default, and the common case)
sealed fieldsciphertext under the space's DEK, plus a blind-index digest per indexed fieldopen fields freely; sealed fields only by decrypting at query time, one row at a time
client-held keysciphertext only; the wrapping key never reaches the platformnothing sealed, ever, even to service the account

Each stop builds on the previous one: a space runs under custody: managed by default, individual fields opt into sealed, and at the far stop the DEK itself is wrapped by a key the platform never holds.

Sealed fields and blind indexes

A sealed field lives in the space's encrypted payload instead of a plaintext column. Add indexed and the write also computes an HMAC digest, keyed per space and per field, into a field$bidx column, so equality lookups run at ordinary SQL speed without the key ever touching the database.

normalize(lower) decides what "the same value" means before any of that happens: lowercase plus Unicode NFC, applied on write and on every query term, so Alice@Example.com and alice@example.com seal to the same digest.

market.ordo
entity customers {
  name:  text
  email: text?  sealed indexed unique normalize(lower)
}
import { entity, t } from '@hominemai/ordo-cdk';

const customers = entity('customers', {
  name: t.text(),
  email: t.text().optional().unique().sealed().indexed().normalize('lower'),
});

Enables:

  • == and in comparisons at SQL speed, with no key material touching the database
  • unique constraints on a sealed field, checked against the digest
  • converge-or-create writes that address a row by a sealed key, such as upserting a customer by email

Refuses to compile:

  • range queries like email > "a@"
  • substring search: email contains "example" runs post-decrypt only, at unbounded cost
  • sorting: sort email refuses, because a hash carries no order to leak
The NULL sentinel. A nullable sealed indexed unique field can't just store SQL NULL in the blind-index column because Postgres treats every NULL as distinct, so a unique constraint would admit unlimited nulls. Ordo stores a reserved, deliberately non-UTF-8 sentinel instead, so at most one null row is admitted, exactly as the language spec requires.

Crypto-erasure

Every sealed value is wrapped under its space's current epoch key. Destroy that epoch's key, and every value sealed under it becomes unreadable everywhere at once (in the primary, in replicas, in backups) because the ciphertext was never anything but noise without it. There is no row to hunt down and no copy to chase; the key is simply gone.

Crypto-erasure makes deletion provable. Destroy the epoch key and every value sealed under it becomes unreadable everywhere at once, and the absence of the key is something you can show.

The command log

Under every write sits a per-space hash chain (SHA-256, from a genesis of zeros), and the chain is what makes the rest of this guide's claims checkable rather than asserted.

Visualize this · tamper with the chain

Append, then converge

A command is attributed to a principal and versioned before it ever becomes a row. It lands on the space's chain first (appended after the previous block's hash), and only then is it applied to produce the row you read back. The row is a projection of the chain, not the other way around.

Verify and checkpoints

Verification replays the chain and confirms every hash matches the command before it. An edit made behind the platform's back cannot hide because it would break the chain at the point it was inserted. Periodically, a checkpoint is signed with Ed25519, so a verifier doesn't have to replay from genesis every time: it can start from the last trusted checkpoint and only walk forward.

No raw UPDATE path

Ordo's grammar has no UPDATE keyword; the parser simply doesn't recognize the token, so the path is closed before any runtime enforcement could be needed. A write is either set (create-or-converge) or del, with no third shape that mutates a row in place without going through the chain.

refused at parse time
# Ordo's grammar has no UPDATE statement
update customers set tier = "gold" where id == "cust_01J9K2QW"

Automation

Every trigger in Ordo reduces to two primitives, and both see only shape and time, never the envelope or the values inside.

Two primitives

A listener matches the command envelope only (event kind, space, entity, actor), fields that sit outside the encryption boundary by construction. A clock fires on a cron-grade schedule. Nothing else exists; there is no "if amount > 500" trigger clause, because a trigger never sees a value.

Modifiers attach to either primitive without needing data: debounce <duration>, coalesce, and rate caps.

triggers.ordo
when finance.transactions.ingested -> run spendWatch    debounce 60s
every day 02:00Z                   -> run nightlySweep

# listener pattern: <domain>.<entity>.<kind> — shape, never values
// when / every / trigger: not yet offered by the builder — authored in .ordo

Everything is an event

Webhooks, cron, inbound email, SMS, and a user's click are none of them special cases in the trigger layer. An outsider is just a write-only source: principal, and its append fires ingested like any other create. Five very different rivers, one bed: they all resolve into a listener or a clock before a routine ever runs.

The event vocabulary

A listener pattern is <domain>.<entity>.<kind>, and <kind> comes from a closed vocabulary; an unrecognized kind is a compile error, not a pattern that silently never fires.

KindFires on
createda command whose mode created the row
convergeda command that changed an existing row
deleteda row removal, including a subtree cascade's per-row commands
writtenthe union of created, converged, and deleted, the common case and one word
ingesteda create attributed to a source: principal (a webhook, a sensor, a mail slot)
feda write attributed to source:feed-*, which is an inter-space feed copy landing
reverteda group revert touching the entity

Taming the stream runs today

Debounce is trailing-edge: the run fires a fixed duration after the last matching event in a burst, with a declared maximum wait so a continuously noisy source still eventually runs.

Coalesce caps pending runs at one, so a burst of matching events collapses into a single queued run instead of one per event.

Dead-letter catches a run that keeps failing and sets it aside instead of retrying forever or dropping it silently, so a broken or noisy source can't take the routine layer down with it.

The provenance bound

A routine woken by a listener may only touch rows reachable from $trigger.ids, the identifiers of whatever actually matched, unless it separately declares broader scope. This is R-G20: being woken by an event is not, by itself, a grant to read or write anything else in the space.

Status. The trigger runtime (event derivation, envelope matching, batching, debounce/coalesce, dead-letter, and the provenance bound) is built and Postgres-tested today. Three named seams remain before it runs end to end without hand-holding: the source-level declaration spelling (how a listener's source is written down), the always-on worker that keeps the runtime running continuously, and the outsider-attribution producers that stamp source: on inbound webhook, email, and SMS writes. Routes, the push, SMS, and email fallback chains, have no code yet settled spec · not yet built.

Sharing & the interface

Data leaves a space in exactly two ways: a consented feed between spaces, or a caller-scoped API described by a descriptor the compiler emits.

Consented feeds settled spec · not yet built

A feed is one-way standing replication of a named query from one space into another. Both spaces have to consent, the sender to send and the receiver to receive, before a single row moves. Copies land as ordinary writes, attributed to source:feed-<name>, which is what lets the receiving space's own triggers fire on the arriving data exactly as they would on a local write.

Withdraw consent on either side and the river simply stops; nothing is deleted, no history is rewritten, the copies just stop arriving.

The Interface Descriptor runs today

The compiler emits an Interface Descriptor alongside the schema and the API: a golden-tested, caller-scoped artifact describing exactly which ops a given caller can see, their parameters, and their output shape. Nothing about it is hand-written or guessed at by a client; it is a direct projection of what the compiler already proved about your definitions.

@hominemai/ordo-react is the first consumer, and it's headless: everything is wired (fetching, paging, live updates, the typed calls themselves) and nothing is rendered. You bring your own components; the descriptor and the runtime just make sure they're never guessing about what's callable.

TypeScript & the comparison

A typed door into the same grammar, and an honest look at what that costs and buys against a save-and-it's-live baseline.

Two doors into one room runs today

@hominemai/ordo-cdk is a typed TypeScript builder for the same grammar this guide has been showing in .ordo text. You call entity(), op(), and the rest of the builder from ordinary TypeScript, and synth() emits canonical .ordo text. That text, not the TypeScript that produced it, is the artifact that is reviewed, diffed, committed, and deployed.

Everything downstream of that emitted text is unchanged: same compiler, same manifests, same cost classes, same registry. The platform never knows which door a definition came in through. .ordo text and the builder are two doors into one room: one grammar, one compiler, one meaning.

vendors.ts
import { domain, entity, op, synth, t, f, lit, src } from '@hominemai/ordo-cdk';

const vendors = entity('vendors', {
  name: t.text(),
  region: t.text(),
  active: t.bool().default(lit(true)),
});

const activeProducts = op('activeProducts', {}, (b) =>
  b.source(src('products').args(f.active.eq(lit(true))).pick('name', 'price')),
).unbounded();

console.log(synth(domain('market', '1.1.0'), vendors, activeProducts));
domain market @ 1.1.0

entity vendors {
  name: text
  region: text
  active: bool = true
}

op activeProducts unbounded =
  products(active == true)[name, price]

The package keeps a hard boundary between two halves: a hand-written skeleton (the chaining shape, the argument order, the IR) and a generated vocabulary, every word regenerated straight from the parser's own tables whenever the language changes. A shape is a human decision; a word is the generator's. That split is what keeps the builder from quietly drifting out from under the grammar it fronts.

Three gates, one ratchet. A new keyword has to clear all three before anything ships: cargo build fails if a word added to the lexer has no builder decision recorded against it; npm run check fails if a decision has no implementation; and the isomorphism corpus fails if an implementation says something the parser refuses. The corpus translation is machine-written rather than hand-picked: it walks every AST node the grammar can produce, so a builder that can say more or less than .ordo can fails the build instead of shipping quietly. Score today: 31 of 31 corpus programs round-trip clean.

Compared to Convex

Convex's loop is real, and it's the right bar to name honestly: edit TypeScript, save, and the change is live in under a second, with errors inline in the editor. That loop is the developer-experience bar for this category, and Ordo doesn't pretend otherwise.

What Ordo charges that Convex doesn't is a registration ceremony: a definition is planned and apply'd rather than just saved, and every write is a named, versioned op instead of a query assembled at the call site. What that ceremony buys is a deterministic, closed surface: per-space custody and an audit chain under every write, no free-form query for a caller to construct at runtime, and a grammar narrow enough that an LLM either emits it correctly or fails loudly against a rule it can read and repair, rather than drifting into something that quietly keeps running.

With the CDK, the authoring language is the same TypeScript either way; the difference is what happens after you hit save.
