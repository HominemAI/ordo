The three to read first

S6-001

A permission rule is skipped whenever the compiler adds a table by itself

Critical · seen live

When a query names two tables that only connect through a third, the compiler adds the third automatically. It does not apply the third table's permission rule.

The reviewer reproduced it against the running system: a member saw which person was assigned to which place, where the assignment belonged to somebody else and their own rule forbade reading it. The owner and the non-owner received identical results.

It is the same mistake as one we already knew about, on a second path that was recorded nowhere. The description the system publishes about the operation says the rule is applied, so anyone auditing from that description would have been told it was safe.

Needs from you: a go. The ruling already exists and covers both paths.

S6-002

Suspending a member does nothing

Critical · seen live

The front door decides who may do what from a list it reads at startup. That list leaves out whether a member is suspended, so everybody is treated as active, and no operation exists that suspends anyone. The reviewer marked a member suspended in the database; they kept full access.

Removing a member does work, at the next restart or deploy. Until then they are still served.

Our operator guide said suspension was immediate by construction. It now says what is true, and how to cut somebody off today: remove them and restart.

Needs from you: what suspension and removal should mean, and how fast.

S6-003

Encrypted values can be moved between records undetected

Critical · read in code

Every protected value is locked in a way that records which column it belongs to, and not which row. Somebody holding the database, who cannot read a value, can copy it onto a different record and it opens there as if it had always been there. Stored files behave the same way.

That is precisely the person the key design exists to constrain. They still cannot read anything. They can rearrange it.

One thing is not yet known: whether the audit history would reveal the move afterwards. Nobody has checked, so it is listed as a question and not assumed either way. If it would, this drops to Major.

Needs from you: whether to bind each value to its own record. Now is the cheap moment: nothing is deployed, so it costs no migration.

The cause behind three of them

The reviewer's hardest objection was to a design choice rather than a bug: the front door works from a snapshot of who the members are, taken at startup. Suspension being ignored, removal being slow, and a membership change that tells nobody are all consequences of that one decision. The code admits it in a comment, calling itself weaker than its own documentation.

S6-006

Something I told you about it was false

Major

I said a changed bundle under a name already used would be refused. That is only true if the record ids changed. If the ids are the same and the contents differ, a re-run carries on, keeps the old contents for what it already loaded, takes the new for the rest, and reports success over the mixture.

The claim was in the original plan, and I repeated it to you without checking what the comparison actually covered. Corrected in five places.

S6-007

Two records with the same unique key are quietly merged

Major · yours

They should be refused. A loader for somebody else's data that cannot reject a duplicate is how a migration ends with fewer records than it began with and nobody noticing. The code says so in its own comments and had put the question off.

Needs from you: refuse or merge. I recommend refuse.

S6-008

No size limit on anything it reads

Major

Every file in a bundle is read whole into memory, attachments included, before any limit is consulted. One oversized file exhausts the machine before a refusal can fire.

What held when attacked

As important as the findings, because a repair must not break any of it.

  • The fix from last week held. The reviewer looked for a second place where history could be signed without being verified first, and found none.
  • Keys. The sealed master file, the way retired keys are genuinely destroyed rather than merely forgotten, and the rule that key material never leaves the component that holds it.
  • Tokens. Checked in constant time, authenticity before content, and an old format cannot be passed off as current.
  • The front door's single answer. An operation that does not exist and one you may not call look identical, so guessing reveals nothing.
  • Deleting a tenant. Keys are destroyed before rows, so an interrupted deletion leaves nothing readable.

Where my own earlier work was wrong

Three things, stated plainly since they change how much weight yesterday's trace deserves:

  • The trace said no contradiction between documents and code had been found. The review found fifteen. A trace asks whether a mechanism exists, and does not ask whether it is right. My sentence read as though it had asked both.
  • Its summary counts were wrong: nine and nine, where it said eight and ten.
  • I guessed that the finding about tokens not being tied to a device was probably closed. It is still open.
