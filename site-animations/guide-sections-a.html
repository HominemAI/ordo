The whole pitch, in one file

A closed, deterministic definition language — and a platform — compiling to Postgres.

Ordo is a grammar with one spelling per concept: one way to declare a shape, one way to read, one way to write. You author a .ordo file; the compiler derives the schema, the typed API, the permissions surface, the audit log, and the scheduled jobs from it. Nothing about the running app is hand-wired — it all falls out of the source.

The bet behind that rigidity is specific: a grammar strict enough that an LLM either emits it correctly or fails loudly is also the grammar humans can trust. There is no partial credit for a program that almost parses, and no silent fallback when a statement is ambiguous — the compiler stops and names the problem.

Here is a complete, working single-user app — a plant-watering tracker — start to finish:

plantcare.ordo
domain plantcare @ 0.1.0

entity plants {
  name:      text
  room:      text?
  everyDays: duration(ms) = 7d      # watering cadence
}

entity waterings {
  plant -> plants   owned
  at:    date
  by:    text = ""
}

entity alerts {
  key:      text unique             # upsert-by-key lifecycle
  severity: text = "warning"
  title:    text
  status:   text = "active"
}

op thirsty($today: date) =
  plants[name, room, everyDays]  waterings[at]
  sort -waterings.at
  take[plants.id] 1
  | (at <= $today - everyDays) or at is null

op history($plant: id) =
  waterings(plant == $plant)[at, by]
  sort -at
  take 30

op water($plant: id, $by: text, $today: date) =
  set waterings { plant: $plant, at: $today, by: $by }
  set alerts(key == "thirsty:" + $plant) { status: "resolved" }

op addPlant($name: text, $room: text) =
  set plants { name: $name, room: $room }

op pruneLogs($before: date) =
  del waterings(at <= $before)

# routine & route: settled in spec, source spelling being finalized

routine thirstCheck in plantcare {
  trigger every day 09:00Z
  run($today: date):
    each -> set alerts { key: "thirsty:" + plants.id,
                         title: name + " needs water",
                         status: "active" }   # restate so resolved alerts re-raise
}

route alerts.warning -> [push] fallback email

That single file is the whole app description. Two commands turn it into a running system — ordo plan shows you the derived diff before anything happens, and ordo apply registers it.

What you get

  • Typed API ops, one per declared op — nothing else is callable
  • A derived Postgres schema, with your identifiers surviving verbatim
  • A generated UI descriptor from shapes and ops — headless, nothing rendered
  • A runtime permissions surface — role→op profiles, changeable without a redeploy
  • Audit machinery — a hash-chained command log under every write
  • Scheduled routines and event routing, once routine/route land
Pre-alpha, spec-first. The parser, DDL lowering, API surface, and command log run today. routine/route source spelling, the always-on worker that fires them, and outbound egress (push/email/SMS) are the named seams still being closed. Nothing here is installable yet.

The language

Shapes, typed ids, pipelines you can watch, and two write verbs — one spelling each.

Ordo's grammar covers four things: how you declare a shape, how a row gets its id, how you read, and how you write. Each has exactly one spelling, and each refuses rather than guesses when a statement doesn't fit.

Shapes

A shape is the whole story of a row — type, default, optionality, even custody — declared once, in place:

text? marks a field optional; anything without a ? is required. Defaults are written as literals, so tier: text = "basic" is the entire default — nothing is computed at read time. customer -> customers is a real, space-carrying foreign key, not a naming convention the reader has to trust. sealed on memo means that field is ciphertext at rest.

Every entity is sealed-aware and unique-aware in the same breath as its type — there's no separate constraints block to fall out of sync with the field list.

market.ordo
entity customers {
  name:  text
  email: text?  sealed indexed unique normalize(lower)
  tier:  text = "basic"
}

entity orders {
  customer -> customers
  placed: date
  status: text = "open"
  total:  money
  memo:   text = ""   sealed
}

Typed ids

Every row's id is entity-prefixed and time-ordered — plnt_01J8… — and the server generates it; nothing in Ordo lets an author choose one. The prefix is derived from the entity name so that any id you see anywhere, in a log line or an audit entry, is self-describing without a lookup.

Derivation splits the name at camelCase boundaries, abbreviates each word, and joins with a hyphen — orderItems becomes orde-item. Two entities may never land on the same prefix; a collision is a compile error naming both offenders:

compiler
[id_key_collision] `orders` and `orderings` both derive id key `orde`
— give one an explicit key: `entity orderings (key: …)`

Reads are pipelines

A read is a pipeline you can watch: filter, shape, sort, cut — evaluated in exactly the order written. There's no free-form SQL underneath it; what you spell is what runs.

market.ordo
op openOrders($cust: id) =
  orders(customer == $cust
         and status == "open")[placed, total]
  sort -placed
  take 3

Writes: two verbs, derived modes

There is no insert, update, or delete keyword. There are two verbs, set and del, and the write mode is derived from the statement's condition, never spelled separately:

tasks.ordo
op addTask($project: id, $title: text) =
  set tasks { project: $project, title: $title }

op renameTask($task: id, $title: text) =
  set tasks(id == $task) { title: $title }

op purgeDone($project: id) =
  del tasks(project == $project
            and status == "done")
ModeWhat triggers itExample
Createno condition — nothing to address, so this makes a rowset tasks { project: $project, title: $title }
Addressedid == … — exactly one row, namedset tasks(id == $task) { title: $title }
Bulkany other condition — a range, however many rows that isdel tasks(project == $project and status == "done")
A delete always states its target: bare del tasks does not parse. Delete-everything is spelled del tasks(true) — the same statement, said on purpose, so it's something a reviewer greps for rather than something a dropped condition quietly becomes.

Refusals are the feature

When a statement can't be honored honestly, the compiler stops and names the problem — it never approximates or falls back to something close:

compiler — messages abridged for illustration
del tasks
  → [parse_error] a delete always states its target — delete-everything
    is del tasks(true), said on purpose

orders(customer == $cust) sort memo
  → [sealed_unsupported] `memo` is sealed — the blind index answers
    equality only, not sort

entity orderings { … }
  → [id_key_collision] `orders` and `orderings` both derive id key
    `orde` — give one an explicit key

Every one of these is a compile-time refusal, not a runtime surprise — you find out before you ship, not from a support ticket.

From source to Postgres

A two-command contract, exact DDL, and tenancy that lives in the keys, not a WHERE clause.

Ordo doesn't hide the database — it derives it. Every entity you declare becomes a real Postgres table, and the compiler shows you exactly what it will build before it builds anything.

plan, then apply

ordo plan derives the schema, the API, and the access surface from your source and shows the exact diff — additions, drops, and everything in between, before anything happens. ordo apply takes that plan and stores it as a versioned artifact in the registry.

apply does not run DDL against your database. It registers a versioned, compiled program. What turns that artifact into running schema and endpoints is a separate concern from the language itself — apply's job stops at "this program is now the registered one."

The lowering

Every field lowers to a typed column, with your identifiers surviving verbatim and double-quoted — the same spelling in source, schema, and the command log. A duration(ms) literal like 7d becomes a plain integer of milliseconds, so there's no unit bug waiting in a join.

plantcare.ordo
entity plants {
  name:      text
  room:      text?
  everyDays: duration(ms) = 7d
}
derived DDL
CREATE TABLE "plants" (
  "$space"    text   NOT NULL,
  "id"        text   NOT NULL,
  "name"      text   NOT NULL,
  "room"      text,
  "everyDays" bigint NOT NULL DEFAULT 604800000,
  PRIMARY KEY ("$space","id")
);

Two columns appear on every table whether or not you declared them: "id" and "$space". The primary key is always the pair ("$space","id") — which is what makes tenancy structural rather than a convention someone has to remember to apply.

Tenancy is structural

"$space" rides in every primary key and every foreign key. A row in one space cannot reference a row in another, because the reference itself carries the space it was made in — there's no query path that lets it happen by accident.

The API

Ops are the only callable surface — typed, versioned, and nothing else exists to call.

There is no free-form query endpoint. Every callable thing in an Ordo app is an op you declared, and each one compiles to exactly one route.

Ops are the only surface

Each op becomes /op/{name} — singular, never /ops/. Reads use GET; writes use POST. Params are validated at the door, and the response is shaped exactly the way the op's query says.

OpMethod & pathParams
thirstyGET /op/thirsty$today: date
historyGET /op/history$plant: id
waterPOST /op/water$plant: id, $by: text, $today: date
addPlantPOST /op/addPlant$name: text, $room: text
pruneLogsPOST /op/pruneLogs$before: date

Nothing you didn't declare is reachable — there's no ORM escape hatch and no admin query console sitting next to it.

Calling an op

Parameters travel as a bare-keyed JSON body — no envelope, no wrapper object:

request
POST /op/water
{"plant":"plnt_01J8…","by":"adam"}

Every response carries a per-op version header. If the client's compiled understanding of an op has drifted from what's currently registered, the response comes back flagged rather than silently mismatched — including x-ordo-version-skew for callers paging through a result set whose shape changed underneath them.

What you can't see can't hurt you

Authorization is not a line in your source — it's runtime platform data: role→op access profiles plus capability allowlists, looked up on every call.

A refused call and a call to an op that was never declared return the same 403 access_denied, byte-identical. There is no signal in the response that distinguishes "you're not allowed" from "that doesn't exist." And the per-caller catalog doesn't mark what you can't reach — it simply omits it, so probing the catalog itself leaks nothing about what exists elsewhere in the app.

Access profiles runs today

Profiles map roles to the ops they can call. For plantcare, a natural progression looks like this:

RoleCan call
viewerthirsty, history
editor+ water
manager+ addPlant
owner+ pruneLogs

These four roles — owner, manager, editor, viewer — are the complete set; nothing in the language lets you invent an "admin" or a "member" role. Because profiles are runtime data rather than compiled syntax, you can widen or narrow who calls what without a redeploy — the source that declared pruneLogs never has to change for an owner to be promoted to a manager, or the reverse.
