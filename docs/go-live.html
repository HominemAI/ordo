Ordo Go-Live

Four things stand between the instance in the cluster and a deployment serving real callers. Three of them are yours, and none of them is a missing capability.

The machine has been up since 20 September with no program on it. ordo.inf.smg.icu boots, creates its own platform tables, mints custody for the system space, and serves. Every step below has been exercised and has a test holding it. What is left is a decision, two configurations and a release.

What I need from you, and what I never want

I need to know when each step is done, not what it produced. Not the passphrase, not the master key file, not a token, not a password. If any of those ever appears in our conversation it has to be rotated, so the answer I want is always just done.

What the first program actually is

This is the one that gates the ordering of everything else, which is why it is first even though it involves no commands. It is on the board as first-program.

My recommendation: something you actually use, with guards and more than one member. The example I built, examples/first-app, is one table with one field and no guard. It proves the whole path end to end and proves almost nothing else. A first deployment that never exercises who-may-read-which-row leaves the part the entire argument rests on untested in production.

What the program contains decides which of my open work is blocking:

  • Carries data from an old system: the import verification pass becomes a gate. Without it a migration finishes and nobody can say whether it worked.
  • Has nightly or reactive rules: the trigger declaration spelling becomes a gate, and that is a ruling only you can make. The workers are built and registered; nothing can declare one.
  • Has a browser page: the CORS question becomes a gate. No page on another origin can call a deployment today.
  • Has file attachments: nothing. That was a gate until 26 September and is closed.

What the program is, and whether it has any of those four things.

Yours · secrets

Mint the deployment's custody

Two commands, on the machine that will run the deployment. The first mints a master key and writes it sealed under a passphrase, so the file on disk is useless alone. The second creates a space's own keys.

# 1: the master key, sealed under a passphrase you supply in a FILE
ordo keys seal-master \
  --out /etc/ordo/master.sealed \
  --passphrase-file /run/secrets/ordo-pass

# 2: the first space's custody, using that sealed file
ordo keys init --space system --as you \
  --master-key-file /etc/ordo/master.sealed \
  --passphrase-file /run/secrets/ordo-pass

The passphrase comes from a file and not a flag, deliberately: a flag is in your shell history and in the process list where anyone on the box can read it, and a prompt cannot be scripted. seal-master prints the key id and a fingerprint, and never the key. It refuses to overwrite an existing file.

Then the deployment boots from the sealed file, with the master itself nowhere in its environment:

ORDO_KEY_PROVIDER=sealed-master
ORDO_MASTER_KEY_FILE=/etc/ordo/master.sealed
ORDO_MASTER_KEY_PASSPHRASE_FILE=/run/secrets/ordo-pass
ORDO_SPACE=system
ORDO_TOKEN_KEY=32 random bytes, hex
ORDO_PAGE_KEY=32 random bytes, hex

There is no escrow and no recovery

The property that makes crypto-erasure real is the same property that makes losing key material unrecoverable. Back up the sealed file and the passphrase separately, to somewhere that is not this deployment's database.

And the master key of the first boot is the one everything is wrapped under. A mistyped master on a first boot gives you a system space wrapped under the typo; the next boot under the right master refuses with custody exists but this master key does not open it. The way across is ordo keys rewrap-master, which is transactional and moves no blind-index digest.

What good looks like

ordo-host 0.1.0  addr=0.0.0.0:4000  space=system
  custody     sealed-master  key …  epoch=1
  system      system  (created at boot)
  continuity  system: intact

If the log says custody test (UNSAFE — repository constant) then the provider did not take, and nothing real should be written to that deployment until it does. That line is correct on your laptop under ordo dev and is never correct in the cluster.

Tell me

Just custody is done, plus whether the startup log says sealed-master.

Yours · config

Turn sign-in on

Corrected 29 September: this step is not enough, and I was wrong to present it as one

Turning on password sign-in gives you the sign-in routes and nothing that can use them. There is no way to create a credential in a running deployment: the code that enrols one is only ever called by tests. And a password sign-in can never pass the extra check that deploying a program requires, by design, because a password proves a secret and not that a person is present.

What is actually needed is passkey sign-in, which is built and tested as a verifier and is refused by the server at start-up. It is now the first thing to build.

Right now the instance has no authentication surface at all. The /auth/* routes exist only when this is set, so without it there is no way for a real caller to obtain a token, and the only tokens that exist are the ones ordo dev prints locally and signs with a key that dies with the process.

ORDO_AUTH_METHODS=password
ORDO_SESSION_SECS=3600        # how long a token lives
ORDO_SESSION_MAX_SECS=2592000 # how long a session may be refreshed for

password is the only method this binary serves. It will refuse to boot on any other value. It will not start with an authentication surface it cannot honour.

A token comes from a sign-in, not from a printed line:

curl -s https://ordo.inf.smg.icu/auth/begin  -d '…'
curl -s https://ordo.inf.smg.icu/auth/complete -d '…'

Auth is on, and I will check that a sign-in round trip works against the live door.

Tag a release that actually publishes

This is the last open item on the CI checklist: nothing has ever published a release page. Until one does there is no pinned image to deploy by digest, only a build somebody made by hand.

git tag v0.1.1
git push origin v0.1.1

Why the last one did not publish, since it looked like it should. The v0.1.0 tag ran the release workflow twice. Both times every Linux and arm64-macOS leg finished, and both times the x86_64-apple-darwin leg sat queued for twelve hours, then nine, because its runner label is GitHub's last Intel image and does not schedule for this account. The release job needs every binary, and a job that can never start is indistinguishable from one that has not started yet. No gate catches that, because a drill proves a job fails and never that it runs.

That target was dropped on your reading that we build on GHA to run on Linux, so a fresh tag should go green. The release notes also used to claim a build-provenance attestation that this organization cannot attach; they now say plainly that provenance and the Intel binary are both missing.

Nothing. I will watch the run and report. Push the tag when you are ready for it.

Then the program goes on

This does not work today

Deploying over the door needs a token that proves a person is present, and the only sign-in the server offers cannot produce one. The tests that show this command working create their tokens directly and do not sign in. Until passkey sign-in is switched on, a program can be applied only with direct database access, which is the break-glass path.

Once custody exists and a program is chosen, deploying it is one command against the door. No database password on a laptop, and the actor recorded is the principal your token proved.

ordo apply ./yourprogram.ordo \
  --host ordo.inf.smg.icu \
  --space system \
  --token $ORDO_TOKEN

On a database with no program the boot mints custody and the log says custody only, because the system space's founding member row needs the members table that a program's DDL creates. The first apply writes that row on the swap it triggers, with no restart:

system space system: founding row written

Then ordo plan --against shows what any later change would do before it does it, and refuses, and does not warn, whenever a probe comes back non-empty, because which row survives is your decision.

What I am deliberately not doing yet

What I am holding:

  • The import verification pass. Waiting on step 1, because it only matters if the first program carries data.
  • Triggers that fire. Waiting on your ruling. The supervisor and all four trigger workers are built and registered; the language has no way to declare a listener, and two documents spell that declaration two different ways, so building either would decide it by accident.
  • CORS at the door. Built as you ruled, an origin allowlist. Nothing is set by default, so only a page on the deployment's own origin can call it. If your page is served from another origin, such as a Cloudflare Pages site, set ORDO_CORS_ORIGINS=https://your-page.example on the deployment, or the browser will discard every answer without an error you can see. The setting in the console is not built yet.
  • The last of the CLI audit. An hour of work: ordo fmt is promised in two documents and does not exist, and the usage text still omits quota and usage.
