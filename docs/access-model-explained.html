Where data that is not one tenant's lives

A working document, not a settled one. It follows the 2026-09-12 rulings on the third home and the tenancy topology through the code, and reports where they hold, where they need amending, and where a rule exists in the language with nothing behind it. Every claim cites the file it was checked against.

control plane system space tenant space refused, or missing proposed here

1 · The three homes, and the test that separates them

Ordo names two places data can live and needs three. The control plane holds identity, authentication, access profiles, grants and share grants, plus the attachment tables and the job queue (docs/plan-space-routing.md §3). None of it is modelled as entities and none of it has a chain: AccessEngine is an in-process structure the door consults (crates/ordo-identity/src/access.rs:644), not a table a query can reach. Tenant spaces hold customer data, one chain each, guards compiled into every read. Between them sits content the platform itself authors and everybody reads: a tool catalogue, system agents, reference data. Today it has nowhere to be.

The fill ruled on 2026-09-12 is a system space: an ordinary space, platform-owned, with a universal read window. It inherits a chain, guards, versioning, deploys and export with no new entity kind and no placement syntax, and its only distinguishing properties are that nobody erases it and everybody reads it.

The placement test is authorship

A third party is itself a tenant. What they publish belongs in their own space and is shared outward. The ruling's reason is attribution: a platform-owned space holding their listing would make the platform the author of record for something it did not write.

The conclusion holds. The reason needs amending. The chain would in fact attribute the row correctly. A third party writing into a platform space would do so as a guest, and the corpus pins that a guest is "attributed in the granting space's chain as themselves" (definition-language.md, Inter-space sharing). Bootstrap separately refuses any synthetic actor: the genesis group carries "no unguarded in it and no synthetic 'the platform did this' actor". So the row-level attribution is safe either way. What is not safe is everything that follows the space rather than the row: custody, jurisdiction, the data-encryption key, export and erasure are all per space and owner-gated. A third party whose listing lives in the platform's space cannot export it, cannot erase it, and holds no key over it. Authorship is the right test; custody is the stronger argument for it.

Two consequences of "an ordinary space" that the ruling does not cover

The system space needs a human owner. "A space always has at least one owner, minted at creation," for a human principal, and "pending owner is not a state" (definition-language.md, Space bootstrap). There is no synthetic-actor path. So the deployment's catalogue is owned by a named person.

And that person can delete it. Exit ops "always exist" and are owner-only, step-up gated and command-logged; deletion is the crypto-erasure path. So "nobody erases it" is a property this document would like the system space to have and which nothing in the platform currently provides. Either the system space is exempted from the exit ops (which contradicts "always exist"), or the ownership is held somewhere that makes accidental deletion implausible, and either answer needs stating.

2 · Where the schema sits, and why it forces a decision

Everything in §1 assumes the system space can carry a tools entity that tenant spaces do not have. It cannot, and the reason is in two DDL strings.

CREATE TABLE IF NOT EXISTS "$artifacts" (
  "version" text PRIMARY KEY, "artifact" text NOT NULL,
  "source" text NOT NULL, "ddl" text NOT NULL,
  "applied_at" bigint NOT NULL, "actor" text NOT NULL );
CREATE TABLE IF NOT EXISTS "$activations" (
  "seq" bigserial PRIMARY KEY,
  "version" text NOT NULL REFERENCES "$artifacts" ("version"),
  "at" bigint NOT NULL, "actor" text NOT NULL )

crates/ordo-exec/src/registry.rs:67. Neither table carries a $space column, and the module doc states the consequence in its own words at :15: "$activations records which version the deployment points at, one row per re-point, newest wins."

Every entity table, by contrast, is emphatically per space: primary key ("$space", "id") (crates/ordo-exec/src/undo.rs:233), composite foreign keys, and a planner invariant that "every physical alias is constrained: "alias"."$space" appears" (crates/ordo-plan/src/lib.rs:670).

Put those together. One artifact describes one schema for the whole deployment. The system space is a space in that deployment. So the moment the platform declares entity tools for its catalogue, the tools table exists for every space in the deployment, and every tenant has an empty one. What keeps it empty is the entity's write guard and the door in front of it. No schema boundary is involved.

One capability closes both gaps, and it is not small. Per-space activation ($activations gains a $space) is the single change that would let the catalogue be a schema the system space has and tenants do not, and let a tenant install an app another tenant has not. It touches the artifact registry, the planner's cache, deploy propagation on DEPLOY_CHANNEL (registry.rs:88), and the load gate, which builds its shape verification shadow "from the DDL the artifact asserts its database holds" (registry.rs module doc) and would need a per-space shadow. It also interacts with routing: under plan-space-routing.md the registry stays in the control database while entity tables move to targets, so per-space activation means the control database holds the authority for DDL that has been applied to databases it does not own.

The three ways out, and what each costs

OptionWhat an app may beCostWhat it cannot do
(a) deployment-level apps a package with shapes, installed by the operator none: this is today a marketplace where tenant A installs and tenant B does not
(b) per-space activation a package with its own shapes, per tenant the registry, the planner cache, deploy propagation, the load gate, and the assumption that one schema describes a deployment nothing structural; it is the answer with the largest price
(c) apps are configuration rows over shapes the platform already defines installing is a write anything needing a new entity, a new guard shape, or a new index

The prior decision recommends deciding what an app is allowed to be before choosing between these, and that remains right. One addition from §5 below: the guard grammar interacts with this choice. A guard that enumerates tier names as literals puts the tier ladder in the schema, so under (a) or (c) a creator cannot add a tier without a deployment-wide redeploy. That is a reason to prefer a data-driven tier shape regardless of which option is taken, and it is worked out in §5.

3 · Anonymous and public access

G15 settles the language question and settles it permissively: "anonymous = no principal, hence no members row, hence every guard evaluates false … Unguarded ops do answer anonymous callers (guards are bypassed; the door is a separate layer)."

The door disagrees, and it gets there first.

fn check_access(state, op, space, headers) -> Result<(String, String), ApiError> {
    let token = bearer(headers);
    match token {
        None => Err(door_denial(&op.name, None)),
        Some(token) => match state.access.check(token, space, &op.name) { … }
    }
}

crates/ordo-api/src/router.rs:722, and the blob gate is the same shape at :206. Below it, AccessEngine::check(&self, claims: &TokenClaims, space, op, now) takes claims by reference with no optional form (crates/ordo-identity/src/access.rs:644), and TokenClaims requires a PrincipalId. A token that fails to verify produces a denial recorded as Subject::Unverified with RecordedDecision::TokenUnverifiable and returns AccessDecision::Deny (crates/ordo-host/src/lib.rs:1222).

So this is a settled language rule with no implementation, and the gap is at the door rather than in the guards. There is no representation of a caller who has no principal. Anonymous is not denied by a guard evaluating false, which is what G15 describes. It is denied before any guard is compiled, before the engine is consulted, and before the op is planned.

What a public anonymous path would actually require

Is the anonymous caller a principal holding a grant? The capability machinery fits the authorization question exactly. A grant names one space and carries "an explicit op allowlist, enumerated by a human at grant time on the consent page", which is precisely the sentence "this space's public surface is these three ops". TokenClaims already carries capability: Option<CapabilityGrant> and the capability path is exclusive by token shape, so an anonymous grant would never fall through to roles.

What does not fit is the token. A capability grant is presented as a bearer string, and a public bearer string shipped into every browser is a secret with no secret to keep: it cannot be revoked for one caller, and rotating it logs out the world. So the grant is the right authorization object and the token is the wrong delivery. proposed The door synthesizes claims when there is no Authorization header, binding a reserved per-space anonymous principal to the space's anonymous grant, and AccessEngine::check runs its three layers unchanged. That is one new construction site in router.rs and no change to the engine's logic.

What stops it being an abuse surface

Four things are load-bearing here, and three of them are properties of code that exists.

  • The deny-volume alert does not see allowed calls. ordo_denials_total{space,principal,principal_kind,op} is incremented on denial only, and the door's own comment calls it "the mandatory deny-volume-per-principal-per-space alert's only input" (crates/ordo-host/src/lib.rs). A flood of successful anonymous reads is invisible to it. Anonymous access needs its own rate limit, which is not the access engine's job and does not exist anywhere today.
  • The idempotency cache keys on the resolved principal ("the idempotency cache keys on it (SH-17)", crates/ordo-api/src/router.rs:718). One anonymous principal per space means every stranger shares one idempotency namespace, so an anonymous write is a collision surface by construction: two unrelated callers can be served each other's cached result.
  • Cursors key on the principal too (parse_cursor(state, &space, op, &gate.principal, …), router.rs:750), with the same sharing and the same conclusion.
  • Security-event routing would lose the property that protects it. Today an unverifiable presentation routes to the deployment stream, and the code says why: "route would send an unverified subject to the deployment stream whatever were passed here, which is the property that stops a stranger growing a space's audit spine" (ordo-host/src/lib.rs:1239). If anonymous becomes a principal with a relationship to the space, its denials would route into that space's own stream, and a stranger could grow a tenant's audit spine at will.
Three rules follow, and this document proposes them. It does not report them as settled. (i) Anonymous is read-only, enforced at the door rather than advised, because the idempotency and cursor namespaces are shared by construction. (ii) Anonymous denials route to the deployment stream even though anonymous is a principal of a named space, preserving the property quoted above. (iii) An anonymous grant is an ordinary capability grant with an ordinary consent page, so the public surface of a space is enumerated by a human and is visible in the same place every other grant is.

Whether the browsable case wants a CDN instead

For the catalogue specifically, "publish to static files behind a CDN" is a stronger answer than a live anonymous read, and it converges with something the third-home ruling already proposes for a different reason.

What publishing buys

  • The abuse surface disappears. An unauthenticated read never reaches Postgres, takes no pool connection, and shares no idempotency or cursor namespace.
  • It is the same mechanism as the cross-publisher discovery projection the 2026-09-12 ruling already calls for: "a derived projection in the control plane, rebuilt from what publishers consented to expose, never a source of truth, and pruned when a publisher is erased". One artifact serves both.
  • It sidesteps §4's routing inversion for the catalogue entirely, so a tenant on an attached target does not pay a cross-database read to list the tools (see §4 and open question 4).

What publishing costs

  • Staleness is bounded by whatever invalidates the CDN, and nothing does today. DEPLOY_CHANNEL nudges nodes (registry.rs:88); no channel nudges an edge cache.
  • It serves no per-caller variation, so anything whose answer depends on who is asking cannot be published.
  • Publishing is the disclosure decision. There is no guard behind a published file, and G12's non-enumerability does not reach it.

proposed Publish the browsable catalogue. Reserve live anonymous reads for answers that genuinely depend on the request: a share link's target (already bearer and mandatorily expiring, definition-language.md line 454), a slug or seat availability check, a status page whose value is its freshness. Everything else that is public and identical for every caller is a file.

One structural wrinkle to know before building either

G2 requires that at least one disjunct of a guard reference $caller, and G15 makes every such disjunct false for an anonymous caller. So an anonymous-readable entity must declare access read open. G9 requires both verbs to be declared and allows open as the value of either, so "anyone reads, members write" is spellable, which is what the public half of a paywall needs.

But G9 also pins that open "does not satisfy the guard-bearing test for guest exposure", and an op exposed to guests must be guard-bearing or it is a compile error. So the same public entity that an anonymous stranger may read cannot be exposed through a window to a guest from another space. Two strangers, two doors, and the door that is open is the one for the stranger with no relationship. In practice the guest can use the anonymous path, so this is a wrinkle and not a blocker. It will still surface as a compile error on an op an author has every reason to expect to work.

4 · Sharing: windows against feeds, and two inversions

Ordo has exactly two sharing doors. A window is an ACL row on a subtree: the guest calls the granting space's ops under their own identity, passes exactly the guards that row satisfies, and is attributed in the granting space's chain. Live, revocable, and "revocation closes the window at the next call". A feed is a standing routine replicating a defined slice into the receiving space, where "copies land as ordinary writes on the receiver's chain (source:feed-<name>), so the receiver's own triggers and rules fire on them".

Inversion one: cost, under the routing topology

A window resolves its grant in the control plane and then reads the owner's target. Under plan-space-routing.md that is a second connection to a second database, and it can never be joined against the guest's own rows, because the two sets of rows are in different databases. A feed copies into the receiver's space, after which every read is local and joinable.

In a single-database deployment the window is the cheaper mechanism, because a feed pays for storage and a routine to maintain freshness. Under routing the feed is the cheaper one. The guidance to app authors inverts, which is why it has to be written down rather than discovered.

Inversion two: what revocation leaves behind

This one points the other way, and the two rules collide on the same content.

Neither mechanism makes delivered data go away. The corpus already states the limit of the window: revocation "stops access, not memory (a guest's mirror may hold what it already fetched), stated honestly, never pretended otherwise". And for the feed: "revocation stops the feed, already-copied data stays, stated at consent". So the difference between them on revocation is not clean-versus-dirty. It is how much was already delivered. A window delivers only what was actually fetched, lazily and per call. A feed delivers the entire defined slice eagerly, whether the receiver ever looked at it. For paid content that gap is the whole product: a lapsed feed subscriber holds every back issue, on their own chain, under their own key, in their own jurisdiction, and no act of the publisher reaches it.

So the rule for paid or revocable content is a window, and the reason is exposure minimization rather than clean revocation. Stating it the other way ("windows revoke properly") would be false and would be discovered to be false by the first customer who asks what a lapsed subscriber still holds.

A third path is worth naming because it sits outside both doors. Bulk paid content can be the blob tier: bytes sealed under the publisher's key in the publisher's space, fetched through a reference. That does not change the revocation arithmetic (a fetched file is a fetched file), but it does move large content off the chain, which the 2026-09-12 bulk ruling already recommends for a different reason.

5 · Tiered membership, the Patreon shape

The obvious spelling is illegal and the reason is exact. G1 closes the guard grammar to forward ref hops, reverse collection steps, == against $caller or literals, bare bool fields, and and/or. Then it says so explicitly: "No other operators, no functions, no arithmetic, no !=, no ordering, no in." So subscriber.tier >= post.tier is invalid_guard_walk, twice over: it orders, and its == would be field against field rather than against a literal or $caller.

The corpus does already have an ordered ladder, and checking it changes the argument. acl (read, write, admin) declares levels that are "a full ordering, left to right", and the derived guard tests "the caller holds a level at or above X". It fits G1 because each threshold "compiles to a closed disjunction of == over the qualifying levels inside one reverse step, which is how an ordering fits in G1's closed grammar". So ordering is not missing from the language. It is present, pinned in the schema, and expanded into == disjuncts at compile time.

Three consequences follow, and the third is the one that decides the shape.

The acl ladder does not give a Patreon. It has exactly three threshold positions: first (read), second (write), last (admin). All levels read. So acl (bronze, silver, gold) gives one read threshold, at bronze. The ladder orders writing and administering, not reading, and a paywall is a read gate.

The escape hatch reaches the shape but puts it in the schema. The derived link entity is "queryable, writable, extendable like any entity" and hand-rolled access clauses stay open, so a guard can enumerate the qualifying levels itself: channel.channelAccess(member == $caller and (level == "silver" or level == "gold")). That is legal G1, it is one acl row per supporter, and a tier change is a single converge, because grantChannelAccess is converge-or-create on the unique key. The cost is that "silver" and "gold" are literals in a guard, so the tier ladder lives in the schema. Adding a platinum tier is a schema change, a schema change is a deploy, and by §2 a deploy re-points $activations for the whole deployment. A creator adding a tier becomes an operator act affecting every tenant.

So the group-per-tier shape wins, for a better reason than the one usually given. It is preferred not because ordering is unspellable, but because it is the shape that keeps the tier in data:

entity posts {
  channel -> channels owned
  tier    -> members                 # a members row with kind: group
  body: text
  access read   tier.groupMembers.group(member == $caller)
  access write  channel.channelAccess(member == $caller and level == "admin")
}

The reverse step names its arriving ref (groupMembers.group) because groupMembers { group -> members owned, member -> members owned } declares two refs to members, which is the exact case G1's ambiguous_reverse_step rule was written for. A domain entity may hold a -> members ref (the corpus uses assignee -> members? and owner -> members), and a group is a members row, so tier -> members points at a group. Adding a tier is then a row, not a deploy.

Pressure-testing it, which is where it gets awkward

(1) A supporter must be a members row in the creator's space. G15 is unconditional: no principal means no members row means every guard evaluates false, "as a defined rule, not as a consequence of null-comparison folklore". The Groups section says the same from the other side: "A principal with no members row in the space binds nothing, and every guard evaluates false." groupMembers is per space and both its refs point at that space's members. So every paying supporter holds a members row in the creator's space.

(2) And the only path that creates one is invitation and acceptance. The platform creates members rows "at exactly four moments", and the only one that applies to someone outside the space is guest binding, "when an inter-space share is accepted". The corpus adds: "There is no domain-authored path to minting one." Combined with "Invitation, never enumeration: shares flow link/invite to accept to principal binding", this means becoming a supporter is a two-sided handshake, not a payment webhook. A creator's billing integration cannot mint the membership; it can only invite, and the supporter must accept before any guard passes. A paid signup therefore has a step between "paid" and "can read" that the platform cannot remove.

(3) At scale this is a lot of rows, and a lot of chain. Groups may not nest (group_nesting, depth 1 in v1), so "their tier and below" has to be materialized: a supporter at tier 4 of 5 holds four groupMembers rows, and a downgrade from 4 to 2 is two removals. Every one is an ordinary audited command, so every membership move is a command group appended to the creator's chain under pg_advisory_xact_lock(APPEND_LOCK_NS, space_lock_key(space)) (crates/ordo-exec/src/commandlog.rs:120, :130, :197). Routing does not help: "Routing does not raise any tenant's write ceiling, which is a separate and currently unmeasured limit" (plan-space-routing.md §0.7). A billing cycle that re-checks ten thousand subscriptions on the first of the month serializes through one advisory lock in one space.

(4) The creator learns the identity of every supporter, and there is no version of this shape where they do not. The members row is a row in the creator's own space, readable by the creator, and domains read displayName off a -> members ref as ordinary data. callersOf "resolves through groups, so 'who can call X' stays one exhaustive query and answers with humans, not group names". memberCount on a group row is platform-maintained, so a per-tier headcount is free. And consent "lands in both spaces' chains" at accept, so the binding is a durable record on both sides. Anonymous patronage is not expressible. A supporter who wants their support private cannot have it, and a creator gets a full subscriber list as a structural consequence rather than as a feature. A product built on this shape owes that disclosure at signup.

(5) Two smaller pins that happen to fall the right way. G17 keeps guard-only fields out of outputs, so a supporter cannot probe the ladder through the op (a condition on one is not_output_field) even though the creator reads groupMembers directly as an ordinary entity. And "a guest creating an acl-bearing row gets no auto-grant", so a supporter who comments in the creator's space does not thereby become the administrator of their own comment; the space owner administers it.

(6) One that does not. The public stub of §6 is access read open, and open is not guard-bearing, so the stub's op cannot be exposed to guests. A supporter who is a guest reads the gated body through the guest door and must read the stub through the anonymous door. One page, two doors, and the anonymous one is unbuilt.

6 · Non-enumerability against the paywall

G12 says an addressed read or write on a row outside the caller's read view answers not_found, "byte-identical to the answer for an id that does not exist", and gives its reason: ids leak, and a distinguishable error "turns it into an oracle answering does this row exist, and is it in a space I am not in?".

A paywall's job is the exact opposite. It must say: this exists, here is what it is about, here is what it costs, and you cannot have it. The proposed resolution is a public stub entity plus a gated body entity. It works, with four qualifications.

(a) Does it double every entity?

It doubles every entity that is both advertised and gated, which in a paid-content app is the central one. It does not double the rest. The split brings structure with it, though:

  • The body must declare its own access clause. G6 inherits from the nearest guard-bearing ancestor, and G9 pins that open is not guard-bearing. So a body owned by an open stub inherits nothing and must declare its own guard, and G9 makes that both verbs.
  • Field placement becomes an access decision. Every field is now either advertised or withheld, and moving one across the line is a schema change, which by §2 is a deployment-wide deploy.
  • G3 constrains the tempting shortcut. Guards may not touch sealed fields (guard_on_sealed), so the paywall cannot be "seal the body and call that the gate". In this shape the guard walks membership rather than the body, so it is unaffected, but the shortcut is closed.

(b) What happens to the ?live subscription

Three answers, and one is genuinely good news.

  • Unlock is live, and free. G16 puts guard entities into the op's inlined base-entity set: they "appear in the scope manifest and are subscribed by ?live. A membership or acl write therefore invalidates guarded live queries, permission changes are visible changes." So a client subscribed to the gated body query while it returns nothing is invalidated the moment the supporter's groupMembers row is written. No polling. The non-obvious part is that the client must subscribe to the empty gated query rather than to the stub.
  • A subscription on the stub never fires on unlock, because the stub's rows did not change. A page that renders "locked" from the stub stays locked until something re-reads.
  • At scale it is a re-query storm. The same G16 rule means every membership write in the creator's space invalidates every live query whose guard walks groupMembers, for every subscriber. One supporter joining invalidates every other supporter's live subscription on every tier-gated op, and invalidation here is per entity rather than per row. Worse, the substrate is unproven: the invalidation bus is per database (plan-space-routing.md §0.8), and PgInvalidationBus "is constructed in tests and not in the serving path today", with lib.rs:195-201 already naming the bus, rather than the live_capable flag, as "the honest gate on ?live".

(c) What the stub leaks

Everything it advertises, to everyone, permanently, with no guard behind it: existence, count, titles, timing and publication cadence; which tier each item requires, so the shape of the paywall is public; and the group row ids the tier refs point at. If memberCount ever appears in the stub's output shape, per-tier supporter counts leak too.

And it re-opens enumeration for the advertised half. The stub's id space is public by design. G12 still closes the oracle at the body, because an addressed body read still answers not_found, so an attacker holding a stub id learns nothing more than the stub already told them.

This is a choice that was made. G12 is a rule that a guarded row must not leak through an error class. Publishing is a different act with a different rule. The stub makes the publishing decision explicit and greppable, because access read open is a keyword and "it is greppable: one word, one meaning, findable in every schema review". A reviewer can enumerate every public surface in a schema with one search, which is exactly what a paywall's public half needs and exactly what a boolean isPublic field would not give.

(d) The dependency that decides whether any of it works

The paywall's public half is blocked and its private half is not, which is the wrong way round. The stub is access read open, so G15 says an unguarded op answers anonymous callers. But §3 shows the door refuses before the engine is reached, so nothing anonymous ever gets to the stub. Meanwhile the gated body works today for any caller who has a members row. So the half of the paywall meant to sell is unreachable and the half meant to withhold is built.

7 · What is still open

1. One system space, or several

The catalogue was ruled singular. Whether system agents, reference data and the catalogue share one space is not. Several would separate blast radius and erasure, but the argument that a deploy to one should not re-point the others is empty until per-space activation exists (§2), so today the only real difference is the guard surface and who owns each.

2. Who owns the system space, and what stops them ending it

A space must have at least one human owner at creation, and exit ops always exist and are owner-only. So "nobody erases it" currently has no mechanism. Either exempt the system space from the exit ops, contradicting "always exist", or place the ownership somewhere that makes it implausible, and say which.

3. Discovery across publishers is a fourth sharing mechanism

The corpus pins that "sharing goes through one of two doors" and the 2026-09-12 ruling then proposes a third artifact, a derived control-plane projection, precisely because windows and feeds both require a relationship. Nothing is decided about its shape: how a publisher's consent to be listed is represented (it is neither a window nor a feed), what refreshes it, what it is allowed to contain, and how "pruned when a publisher is erased" is triggered given erasure is a per-space act in a database the control plane may not own under routing.

4. Where the system space sits under routing, and what the universal read window costs

This is new here and it is not in plan-space-routing.md. §4's inversion applies to the system space itself: a tenant on an attached target reading the catalogue through a universal window is a cross-database read, and the catalogue may not be replicated, so the feed escape is closed by the same ruling that created the system space. Colocating the system space on the default target fixes it for the long tail and not for promoted tenants, who are the largest ones and the ones paying for promotion. The CDN publication of §3 sidesteps it entirely for the browsable case, which is an argument for publication beyond the anonymous one.

5. Payment state lives entirely outside Ordo

There is no billing vocabulary in the platform and that is deliberate: policy spaces makes even the space allowance "a counter a service updates", and "overselling is structurally impossible for the same reason seats are". So the mapping from "paid" to "in the tier group" is an external service holding a capability grant on the creator's space, with lag, partial failure and reconciliation. What happens when the provider says lapsed and the group write fails is not a platform question today. Given §5's finding that membership writes serialize through one advisory lock per space, it may need to become one.

6. Anonymous writes, if they are ever wanted

§3's read-only proposal exists because the idempotency cache and the cursor namespace both key on the resolved principal. A public form submission would need a per-request synthetic principal, which is a different design with its own attribution question: what actor does the resulting command group name?

7. Whether the tier ladder may ever live in the schema

§5 chooses group-per-tier because the acl-level shape puts tier names in guard literals and a schema change is a deployment-wide deploy. If per-space activation (§2, option b) lands, that objection dissolves and the acl-level shape becomes both viable and cheaper: one row per supporter rather than one per tier at or below theirs, and one converge per tier change rather than N adds and removes. So §2 and §5 are coupled, and choosing (b) should reopen §5.

8. How a guest reaches the door at all

Found while drawing the four paths. The access engine's three layers are membership roles, per-space access profiles, and capability allowlists. Role has exactly four variants and none is a guest (crates/ordo-identity/src/principal.rs:105), and crates/ordo-identity/src/access.rs contains no occurrence of "guest". The corpus says a guest holds "no role and no profile" and that the compiler enforces guard-bearing ops for guest exposure, which is the guard half. What admits a null-role members row past the door is not settled in the code read for this document. This may be unbuilt rather than undecided, but it should be established before the window path is relied on for paid content.

9. Anonymous denial routing

§3 proposes that anonymous denials stay on the deployment stream even though anonymous is a principal of a named space, to preserve the property that a stranger cannot grow a tenant's audit spine. That is a proposal in this document and not a ruling. It has a cost: an operator investigating abuse against one tenant's public surface reads it in the deployment stream mixed with every other tenant's.

8 · What this document is asking for

Three things need a ruling before any of it is built. (i) What an app is allowed to be (§2), because it decides per-space activation, and per-space activation decides §5's shape and §1's ability to give the system space a schema tenants do not have. (ii) Whether the public surface is published or live (§3), because publishing removes the abuse surface, the routing cost in open question 4, and the anonymous door all at once, at the price of staleness and no per-caller variation. (iii) Whether "revocation stops access" is a promise the product makes (§4), because neither mechanism delivers it and the difference between them is volume.

Everything else in §7 can be deferred without building against a wrong assumption, with one exception: open question 8. If the guest door is unbuilt rather than merely undocumented, the window path is not available today, and §4's conclusion that paid content wants a window is a conclusion about a mechanism that does not yet work.
