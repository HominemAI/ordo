## A. Promised but not built, or only partly

### 1. A blind-index lookup that returns a sealed field fails to compile

**Severity: High.**

- docs/definition-language.md:846-850 says `sealed indexed` gives "equality lookups at SQL speed".
- The board marks serve-sealed-reads (27ao) built.
- The executor test does serve it: `an_indexed_equality_returns_the_sealed_value`, crates/ordo-exec/tests/sealed_reads.rs:376, runs the call `customers(email == "...")[name, email]`.
- The same shape declared as an op fails:
  ```
  op byEmail($e: text) = customers(email == $e)[name, email] take 1
  plan error in `byEmail`: [unresolved_blind_index] `customers.email`'s digest was never resolved
  ```
- Cause: `program_artifact` (crates/ordo-plan/src/artifact.rs:620) skips planning only when the cost class is `BlindIndex`. With a sealed field in the projection the class differs, so `plan()` runs and errors.
- `NEEDS_KEYS_AT_RUNTIME` (crates/ordo-cli/src/lib.rs:189) is meant to tolerate this code. That tolerance is never reached, because `program_artifact` returns `Err` for the whole program.
- `ordo apply` calls the same function (crates/ordo-cli/src/operator.rs:1839, crates/ordo-host/src/schema_apply.rs:124). A program holding this op cannot be applied.
- Projecting only open fields (`[name]`) compiles.

Board: a new Reported fix.
```
python3 scripts/board.py task "A blind-index lookup that returns a sealed field does not compile" <<'END'
explain: `customers(email == $e)[name, email]` as an op fails check, plan and apply with unresolved_blind_index.
- The executor serves the same call; only the artifact build fails.
- Cause: artifact.rs:620 skips planning only for class BlindIndex.
END
python3 scripts/board.py set serve-sealed-reads work=building where="Declared ops that look up by blind index and return a sealed field fail at artifact build (audit-2026-10-09 finding 1)"
```
