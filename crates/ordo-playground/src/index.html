conditions

==  !=  <  <=  >  >=          and · or (parens to mix)
x is null · x is not null      not x
x in ($a, $b)                  active        # bare bool field
name contains "a" · starts · matches
placed since 90d               # trailing window of the execution clock

== and != are TWO-valued: they compile to IS [NOT] DISTINCT FROM,
so null == null is TRUE and null != "a" is TRUE. SQL's = and <>
drop a null row; Ordo's keep it. Ordering (< <= > >=) matches SQL:
a null operand is false. There is no precedence table — mixing
and/or without parentheses is a parse error, not a default.

sharp rules

· bare source in a MULTI-source list contributes nothing (= [])
· sort keys need not be projected (source row scope; dies at group/distinct)
· a caller's sort replaces a callee's; caller filters run AFTER a callee's take
· sealed fields: omitted by *, refused by name
· 3+ sources DO join — the failure you will see is `ambiguous_match`,
  which names every minimal join it found; pick one with `match `
· `match on ` is still unimplemented
